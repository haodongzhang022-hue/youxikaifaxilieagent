# 04 · 游戏引擎阶段化架构指南

> 参考 `dongjiagoushi` 的「架构·总师」与「架构·总师助理」角色方法论，迁移到**游戏开发领域**，
> 形成「游戏·架构·总师」与「游戏·架构·总师助理」。
> 核心新增：**游戏引擎阶段化思维** —— 架构要绑定游戏引擎（Cocos / Unity / UE），
> 且要绑定**游戏阶段**，防止「Cocos 阶段做了 UE 阶段才该做的事」。
> **同样的事情，阶段不对就算错。**

---

## 〇、与通用架构师的核心差异（为什么游戏架构师不一样）

通用架构师（dongjiagoushi 的架构·总师）建模对象是**软件模块 / 接口 / 数据库**；
游戏架构师（游戏·架构·总师）多了一个**横切维度：游戏引擎与游戏阶段**。

| 维度 | 通用架构·总师 | 游戏·架构·总师 |
|------|-------------|--------------|
| 建模对象 | 模块/接口/数据库 | 玩法系统 + **引擎选型** + **阶段边界** |
| 约束来源 | 技术栈/性能 | 技术栈 + 玩家体验 + **所选引擎能力** |
| 决策依据 | 正确性/成本/周期 | 正确性/成本/周期 + **当前阶段该不该做** |
| 最大的错 | 模块耦合错误 | **阶段选错引擎** / **阶段做了不该做的事** |
| 门禁 | 代码质量 | Gate + **阶段边界检查（阶段不对就算错）** |

> **核心铁律：阶段不对就算错。**
> 引擎能力决定「能做什么」；**阶段决定「现在该不该做」**。两者缺一不可。

---

## 一、游戏引擎阶段化三阶段演进

参考 dongjiagoushi 的「架构 3 阶段渐进」思想（粗纲→功能域→细纲，避免一轮直出最大框架），
游戏架构师把**技术栈演进**也分为 **3 个引擎阶段**，每阶段只做本阶段的事，越界即技术债。

```
阶段1【Cocos 阶段】  网页 / 小游戏 / 小程序 —— MVP 验证期，极速出玩法
阶段2【Unity 阶段】  中度游戏 / App 原生 —— 商业化期，画面与并发升级
阶段3【UE 阶段】     3A / 重度实时 —— 极致画质与大规模同屏
```

### 阶段1：Cocos 阶段（MVP 验证期）

| 维度 | 技术 | 边界内（适合现在做） | 边界外（标记「后期重构」，现在别做） |
|------|------|-------------------|-----------------------------------|
| 前端 | **TypeScript** (Cocos Creator) | UI、动画、点击反馈、本地存档、微信/抖音 SDK | 复杂寻路、大量单位同屏、精密伤害公式 |
| 后端 | **Python (FastAPI)** / Node.js | 登录、JWT、云存档、简单排行榜、签到 | 实时战斗校验、高频位置同步、经济防刷 |
| 数据库 | SQLite / MySQL / Redis | 玩家信息、背包数据 | 海量日志分析、实时在线统计 |

### 阶段2：Unity / 团结引擎阶段（商业化与中度游戏期）

| 维度 | 技术 | 边界内 | 边界外（标记「后期重构」） |
|------|------|------|--------------------------|
| 前端 | **C#** (Unity) | 复杂 UI 框架、AssetBundle 热更新、DOTween、中等 A*、状态机 | 极高并发粒子、底层内存池极致优化、硬核物理碰撞 |
| 后端 | **Go** | 高并发 WebSocket、匹配、聊天、公会、活动结算 | 帧同步战斗校验、需共享微观物理的逻辑 |
| 核心逻辑 | **纯 C# 类库** | 伤害公式、抽卡概率、背包运算（**不依赖 Unity API**） | 需跨语言给 C++ 调用的部分 |

### 阶段3：Unreal Engine 阶段（3A / 重度实时）

| 维度 | 技术 | 备注（架构质变） |
|------|------|----------------|
| 前端 | **C++ + 蓝图** (UE5) | TS 和 C# 退出客户端 |
| 后端(网关/社交) | **Go**（复用阶段2） | Go 找到最舒服位置：高并发 IO 型业务 |
| 后端(战斗/场景) | **C++** | 与客户端**同一份源码编译**（核心库上下双编译） |

## 二、渐进式可复用资产（三层资产，防止推翻重来）

只要把**网络协议（Protobuf）**和**核心数据结构**一开始就定义好，前端换引擎、后端换语言，
都只是「替换零件」，不是「推翻重来」。

### 1. 协议资产（Protobuf / FlatBuffers）—— 【永远复用】
- 从第一天就建立独立仓库 `game-protocols`，定义 `message LoginReq { string token = 1; }`
- Cocos+Python / Unity+Go / UE+C++ 全部通过脚本从该仓库生成对应语言代码
- **价值**：协议不崩，前后端换人换语言换引擎，对接成本零

### 2. 数值与配置表资产（Excel → JSON/Binary）—— 【永远复用】
- 策划填的 Excel 表（武器攻击力、升级曲线），工具导出为标准 JSON/二进制
- Cocos 用 TS 读，Unity 用 C# 读，UE 用 C++ 读
- **价值**：策划心血不因换引擎而丢失

### 3. 纯数学/算法资产（伪代码 → 各语言实现）—— 【半复用】
- 核心抽卡、ELO matchmaking 算法
- 前期 Python/TS 快速写 → 中期 C#/Go 规范化 → 后期 C++ 极致化
- **价值**：算法**单元测试用例**永久保留，C++ 重写后跑当年用例结果一致即重构成功

### 贯穿三阶段的三条铁律
1. **协议先行**：前后端全用 Protobuf/强类型 IDL，协议定下除非大版本否则不改
2. **逻辑与表现分离**：不把「播放爆炸动画」和「扣除 100 血」写在一个函数（前者随引擎变，后者跨阶段复用）
3. **Stateless（无状态）优先**：后端尽量无状态，方便从单机 Python 平滑迁到 Go 集群

## 三、阶段边界检查（阶段不对就算错 · 架构师门禁）

这是「游戏·架构·总师」的**新增门禁**。在每个阶段，架构师必须回答以下「边界检查」问题，
任何一条答「是」即判定**阶段错误（技术债）**，打回：

- [ ] 我是否在 Cocos/Unity 阶段**过早引入了 C++ 级复杂内存管理或设计模式**？（过度设计，拖慢 MVP）
- [ ] 我的网络通信是否**直接传 JSON 字符串**？（立刻停，引入 Protobuf，这是平滑迁移的唯一救命稻草）
- [ ] 我是否把**表现层（动画/UI）与逻辑层（扣血/加钱）混在一起写**了？（标记技术债，下阶段拆分）
- [ ] 我的 Go 后端里是否**写入了每帧计算子弹轨迹的逻辑**？（剥离，这部分未来必须交 C++，Go 扛不住也不该干）

**判定动作**：命中任一条 → `[回转]` 打回开发/策划，标记 `[阶段越界]`，要求在当前阶段能力内重做。

## 四、新增角色：游戏·架构·总师助理

参考 dongjiagoushi 的「架构·总师助理」（专角色专用，负责改错改框架，保总师上下文纯净），
迁移为游戏向的「游戏·架构·总师助理」。

### 职责（游戏向改写）
1. **引擎阶段纠偏专项**：当某个功能「技术实现正确，但**阶段/引擎选错**」（如在 Cocos 阶段做了 UE 阶段的实时战斗架构），由总师助理专责纠偏，而非直接压给总师。
2. **改框架专项**：功能验证不通过、小组长已尝试其他实现仍无法达成、需要改框架/改错时，由总师助理承担专项，保总师主线决策上下文纯净。
3. **边界审查落地**：把「阶段边界检查」从纸面规则落为可执行审查，量化记录每个越界点的位置与影响面。
4. **向总师汇报、由总师把关**：涉及「是否做架构调整」由总师判断，总师助理负责落地执行；不适合调整但必须做成时给折中/取舍，仍解决不掉则询问人类。

### 与总师的职责分离（关键）
- **总师**：专注主线决策，走「游戏向架构八步」，定引擎选型与阶段边界。
- **总师助理**：专角色专用承担「改错 / 改框架 / 引擎阶段纠偏」，**不让框架修改污染总师主线决策上下文**。

### 触发协议（三层，沿用 dongjiagoushi）
- **显式 `[触发:游戏·架构·总师助理]`**：最高优先级
- **语义命中**：「改框架 / 改错 / 引擎阶段 / 阶段越界 / 总师助理 / 边界纠偏」即进入本角色
- **rules 固定触发**：仓库最高规则兜底

### 输出契约
```
- 目标进度尺(goal_meters): goal_total / current / distance / delta
- 问题定性(qualify): 改错 vs 改框架 vs 引擎阶段越界 / 是否需上报总师
- 修正方案(fix): 修正点 + 影响面 + 阶段归属 + 是否需折中取舍
- 汇报留痕(report): 向总师汇报 / Issue 评论留痕可核验
```

## 五、进度管理建议（如何纳入进度）

参考 dongjiagoushi 的「目标进度尺（goal_meters）」+「监控哨兵」思想，把阶段化架构纳入进度：

1. **按阶段设里程碑**：Cocos 阶段里程碑（M1玩法原型 → M2垂直切片）→ Unity 阶段 → UE 阶段
2. **阶段越界即打回**：架构师/总师助理发现阶段越界，`[回转]` 打回，**不进入下阶段门禁**
3. **资产库进度单列**：`game-protocols` 协议库、配置表导出、核心算法用例库，作为**贯穿三阶段的长线任务**独立跟踪，不因换引擎而中断
4. **目标进度尺量化**：每个阶段用 `distance = goal_total - current` 量化到「该阶段验收标准」的距离，越界点记录 delta，防目标漂移
5. **监控哨兵盯收敛**：发现「反复在错误阶段做不该做的事」→ 哨兵判定无效努力，`[打断]` 留续跑点，上报总师助理纠偏

## 六、阶段化架构检查清单（架构师每阶段结束时自问）

- [ ] 当前阶段引擎选型是否匹配玩法复杂度和成本目标？（选错引擎=阶段错误）
- [ ] 我是否把「表现层 / 逻辑层」混写？（是 → 标记技术债，下阶段拆分）
- [ ] 网络通信是否用 Protobuf 而非 JSON 字符串？（是 JSON → 立刻引 Protobuf）
- [ ] 我是否在 Cocos/Unity 阶段过早引入 C++ 级复杂内存管理？（是 → 过度设计，打回）
- [ ] Go 后端是否写入了每帧子弹轨迹计算？（是 → 剥离，未来交 C++）
- [ ] 核心算法 / 配置表 / 协议库是否已作为**独立资产库**沉淀，跨阶段可复用？（否 → 补建）

> **这套机制的本质**：用动态语言（TS/Python）冲锋陷阵拿结果，用工程语言（C#/Go）稳固江山做商业，
> 用 C++ 极致压榨做 3A。阶段不同、引擎不同、但**协议、配置、核心算法**永远复用。
