# 02 · 游戏向架构师团队设计

> 融合 `Claude-Code-Game-Studios`（游戏领域纵深）+ `dongjiagoushi`（工程协作横梁），
> 构建一套**面向游戏开发的多 agent 架构师团队**。核心特征是：
> ① 架构师与经理岗位按游戏向改版；② 常规流程 + 条件触发式协作；③ 数据库支撑；④ 共享记忆（只增不改只追加）。

---

## 一、设计原则

| 原则 | 落地 |
|------|------|
| **游戏向架构师** | 架构师不再只做通用软件架构，而是做**游戏系统架构**（玩法/数值/关卡/经济/战斗）顶层设计 |
| **游戏向经理** | 经理做**游戏排期与制作**（里程碑/垂直切片/软封/硬封/资源），融合 DAG 调度 |
| **AI 优先 + 人类俯瞰** | 产出结构化可索引；人类通过二级信息（看板/报告/索引）俯瞰决策 |
| **完整不残次** | 拒绝最小骨架，交付可运行、可验证的完整框架 |
| **主线不丢** | DAG 主线由总师/经理把持，小组并行分支统一向上整合 |

## 二、命名空间：游戏·前缀

沿用 dongjiagoushi 的「一库多角色 + 前缀命名空间」约定，但改为**游戏向**：

- 所有角色统一前缀 **`游戏·`**：`游戏·架构·总师`、`游戏·制作·经理`、`游戏·策划`……
- `@` 后输入「游戏」即自动补全本团队全部角色，便于搜索与召唤。
- 与通用「架构·」团队区分，不重名。

## 四、协作机制（常规流程 + 条件触发）

### 4.1 常规流程（跑完整流程的 DAG 主线）

```
游戏·架构·总师（架构八步：调研→拓扑→可行性→方案→分工→协作→进度→索引）
   │
   ▼
游戏·制作·经理（里程碑规划 → DAG 派活 → 分形小组并行）
   │
   ├── 策划域：玩法→系统→数值→关卡→剧情→战斗
   ├── 程序域：引擎→客户端→服务端→AI→工具链
   ├── 美术域：原画→3D→动画→特效→UI/UX→TA
   ├── 测试域：用例→执行→回归→性能→放行
   └── 运营域：数据→活动→社区
   │
   ▼
游戏·测试·主管（信号灯门禁）→ 游戏·发行·主管（发布）
```

依赖满足即并行（DAG），非直线流水线；任务规模大时分形为多小组并行，统一向上整合交付。

### 4.2 条件触发式（按需引入角色）

三层触发机制（沿用 dongjiagoushi，注入游戏语义）：

| 触发方式 | 游戏向示例 |
|---------|-----------|
| **① 显式声明 `[触发:X]`** | 接力卡带 `[触发:游戏·数值策划]`，凡匹配必须化身该角色 |
| **② 语义向量触发** | 输入命中"经济/产出/消耗"→ 自动召经济设计师；命中"关卡难度/白盒"→ 召关卡策划；命中"数值失衡/方差"→ 召数值策划 |
| **③ rules 固定触发（兜底）** | 仓库最高规则，约束所有 agent |

**典型条件触发场景**：
- 平衡性异常 → 触发 **游戏·数值策划**（调参/回归）
- 性能不达标 → 触发 **游戏·性能分析**（profiling/优化）
- 剧情与玩法冲突 → 触发 **游戏·创意·总监**（支柱裁决）
- 新引擎适配 → 触发 **游戏·技术·总监** + 引擎专家
- 安全漏洞 → 触发 **游戏·安全工程师**

### 4.3 安全护栏 + 回转/打断协议

- ⏸CP1 计划确认 / ⏸CP2 开发确认 / ⏸CP3 合并确认，人类把关
- **回转**：下游发现上游不达标打回（`[回转] 退回:X / 原因 / 下一步`），最多 3 次，超次标 `blocked`
- **打断**：中断发 `[打断]` 留续跑点，凭 `当前进度` 无缝续跑

## 五、数据库支撑

沿用 dongjiagoushi 六表 + collab 多表，注入游戏语义：

| 表 | 游戏向承载 |
|----|----------|
| `agents` | 游戏岗位 agent 档案（role/group/status/spec） |

| `stats` | 聚合指标（并发度/队列积压/活跃数） |

## 六、架构师与经理改版要点（用户核心诉求）

### 6.1 架构师改版（游戏·架构·总师）

通用架构师只处理"软件模块、接口、数据流"；游戏架构师需要处理和思考的是**不同的**问题：

| 维度 | 通用架构师 | 游戏·架构·总师 |
|------|-----------|--------------|
| 建模对象 | 模块/接口/数据库 | **玩法系统**（机制循环）/ 数值模型 / 关卡 / 经济系统 |
| 核心方法论 | 架构拓扑 | 架构八步 + **MDA 框架** + 支柱（pillars） |
| 约束来源 | 技术栈/性能 | 技术栈 + **玩家体验** + 引擎能力 + 手感 |
| 决策依据 | 正确性/成本/周期 | 正确性/成本/周期 + **玩家心理** + 游戏性 |
| 冲突裁决 | 模块间耦合 | 支柱冲突（创作 vs 技术 vs 产能） |
| 门禁 | 代码质量 | **Gate 裁决**（CD-PILLARS/GDD 对齐/数值平衡） |

架构八步（游戏向改写）：
```
调研(游戏品类/竞品/引擎) → 顶层架构拓扑(玩法→系统→数值→关卡→经济全链路)
→ 可行性验证(引擎/性能/手感) → 工程实施方案(里程碑)
→ 分工与协作规则(策划→程序→美术→测试) → 进度对齐 → 索引建立 → 汇报复盘
```

### 6.2 经理改版（游戏·制作·经理）

| 维度 | 通用经理 | 游戏·制作·经理 |
|------|---------|--------------|
| 排期对象 | 功能/迭代 | **里程碑** / 垂直切片 / 软封 / 硬封 / 发布 |
| 调度方式 | 直线任务 | **DAG + 分形多小组并行** |
| 资源协调 | 人/时间 | 人/时间 + **美术资源管线** + 引擎工具链 |
| 风险 | 进度/依赖 | 进度/依赖 + **游戏手感风险** + 玩法验证 |
| 质量门禁 | 测试通过 | **可玩性** + 平衡性 + 性能 + 里程碑验收 |

## 九、游戏引擎阶段化思维（新增 · 参考 dongjiagoushi 架构师+总师助理）

> 参考 dongjiagoushi 的「架构·总师」+「架构·总师助理」方法论，迁移到游戏领域。
> 核心新增：**游戏架构师不仅做玩法/系统架构，还要绑定游戏引擎（Cocos/Unity/UE）与游戏阶段**。
> **同样的事情，阶段不对就算错。**

### 9.1 新增角色：游戏·架构·总师助理

参考 dongjiagoushi 的「架构·总师助理」（专角色专用改错改框架，保总师上下文纯净），
迁移为游戏向的「游戏·架构·总师助理」：

| 项 | 内容 |
|----|------|
| 职责 | 引擎阶段纠偏专项 / 改错改框架专项 / 阶段边界审查落地 / 向总师汇报由总师把关 |
| 与总师分离 | 总师专注主线决策 + 引擎选型定阶段；总师助理专责纠偏，不让框架修改污染总师上下文 |
| 触发 | 显式 `[触发:游戏·架构·总师助理]` / 语义「改框架/改错/引擎阶段越界」/ rules 兜底 |
| 输出契约 | 目标进度尺(goal_meters) + 问题定性(改错 vs 改框架 vs 阶段越界) + 修正方案 + 汇报留痕 |

### 9.2 引擎阶段化三阶段演进

```
阶段1【Cocos 阶段】网页/小游戏/小程序 —— MVP 验证期（TS + Python/Node）
阶段2【Unity 阶段】中度游戏/App 原生 —— 商业化期（C# + Go + 纯C#核心库）
阶段3【UE 阶段】3A/重度实时 —— 极致画质（C++ + Go网关 + 同源C++核心库）
```

每个阶段有明确**边界**：边界内（适合现在做）vs 边界外（标记「后期重构」）。
**核心铁律：阶段不对就算错。** 引擎能力决定「能做什么」，阶段决定「现在该不该做」。

### 9.3 渐进式可复用资产（防止推翻重来）

| 资产 | 复用性 | 说明 |
|------|-------|------|
| 协议资产（Protobuf/FlatBuffers） | 永远复用 | 独立 `game-protocols` 仓库，脚本生成各语言代码 |
| 数值配置表（Excel→JSON/Binary） | 永远复用 | TS/C#/C++ 各读各的，策划心血不丢 |
| 纯数学/算法资产 | 半复用 | 抽卡/ELO 等，单元测试用例永久保留 |
| 贯穿铁律 | - | 协议先行 / 逻辑表现分离 / Stateless 无状态优先 |

### 9.4 阶段边界检查门禁

在 DAG 主线 `qa` 之后新增 **`stage_gate`**（游戏·架构·总师助理）阶段边界审查节点：
- 命中「阶段越界」（如 Cocos 阶段用 UE 架构 / Go 后端写每帧子弹计算 / 直接传 JSON）
- → `[回转]` 打回纠偏，标记 `[阶段越界]`，不进入发布门禁
- 同时校验跨阶段可复用资产（协议/配置/核心算法）是否已沉淀

详见 `docs/04-game-engine-staged-architecture.md`。
