# 05 · 框架开发测试记录

> 用**游戏向架构师团队**完成游戏团队框架的开发，这本身即是测试——
> 验证「游戏·架构·总师 + 制作·经理 + 策划 + 程序 + 测试」这套协作框架能否真实跑通。

---

## 一、测试目标

用游戏向架构师团队，从零完成一个**游戏功能框架**（战斗系统 Combat System）的开发，
验证框架的五项核心能力：
1. 常规流程主线能否跑通
2. 条件触发能否按需引入角色
3. 共享记忆能否以功能单位承载结构化整理内容
4. 只增不改只追加 + 权重递增机制是否正确
5. 数据库/记忆底座能否支撑协作

---

## 二、执行过程

### ① 常规流程主线（DAG）

| 角色 | 动作 | 共享记忆写入 |
|------|------|------------|
| 游戏·架构·总师 | 架构八步：调研→玩法→系统→数值→关卡→经济→里程碑→分工 | content：顶层架构 |
| 游戏·制作·经理 | 里程碑(M1原型/M2切片/M3软封/M4硬封) + DAG派活 + 分形小组 | task：里程碑计划 |
| 游戏·策划·主管 | 系统设计（背包/战斗/任务） | content：系统设计 |
| 游戏·程序·主管 | 实现 backpack.gd / combat.gd，自测通过 | task：实现 |
| 游戏·测试·主管 | 验收门禁（信号灯绿灯） | task：验收 |

### ② 条件触发

程序实现后检测到 **战斗数值疑似失衡** → 自动引入 **游戏·数值策划** 做平衡调优。
（对应三层触发机制中的语义向量触发/规则触发）

### ③ 共享记忆（功能单位 = combat_system）

```
loc://memory.combat_system.content.001  顶层架构
loc://memory.combat_system.content.002  系统设计
loc://memory.combat_system.content.003  平衡调优
loc://memory.combat_system.task.001    里程碑计划
loc://memory.combat_system.task.002    实现
loc://memory.combat_system.task.003    触发信号
loc://memory.combat_system.task.004    验收
```

### ④ 只增不改只追加 + 权重递增

- 修订战斗平衡：技能CD 6s→5s（手感回调）
- **v1 保留**（status=superseded，物理行不删改），**v2 追加**，weight 1.0→1.5
- 检索 relevance×weight：最新追加优先，历史可回溯

## 四、结论

游戏向架构师团队框架**可运行、可验证**，完整实现了 Issue #10 的核心诉求：
- 游戏向架构师与经理（改版）
- 常规流程 + 条件触发式协作
- 数据库支撑
- 以功能单位为粒度的共享记忆（结构化二次/三次整理内容 + 任务 + 技能）
- 共享部分只增不改只追加 + 追加部分权重更高（缓存命中率优化）

后续可在真实游戏项目上扩展：接入完整 49 岗位、接入真实数据库（PostgreSQL）、
接入语义向量触发（memory 引擎）、在 CNB 上以 `@游戏·xxx` NPC 形式部署。
