# C 跨端一致性坑点

> 危害等级：🔴 本仓库核心架构约束就是「**跨端 bit 级一致**」——同一种子 seed 在
> React/Cocos/Unity/UE 四端必须产出**完全一致**的结果。一旦某端走了"自实现"路径，
> 立刻违反约束，golden hash 校验即失败。

---

## <a name="C1"></a>C1 服务端自实现确定性逻辑，未走中间件统一函数

- **现象**：`CombatService._roll_loot` 自己用 `cabi._fnv1a_hash` + `cabi._splitmix64_next`
  拼了一套掉落逻辑，但**未调用中间件暴露的统一函数 `cabi.roll_loot(loot_table_id, seed)`**。
  两端算法不同（物品表/数量/随机消耗序列均不同），同 seed 掉落完全对不上。
- **危害**：违反「跨端 bit 级一致」核心架构约束；golden hash 比对失败；同 seed 四端掉落不一致。
- **复现**：对同一 seed，服务端 `_roll_loot` 与中间件 `roll_loot` 输出对比，不一致。
- **检测**：搜服务端所有确定性计算，确认都调中间件统一函数，而非复制算法。
- **修复**：`_roll_loot` 直接调用 `cabi.roll_loot(loot_table_id, seed)`，删除自实现。
- **本仓现状**：✅ **已命中 C3**。**必须修复。**

---

## C2 各端各自实现随机数/哈希（算法漂移）

- **现象**：C++/Python/TS/CS 各自实现一遍 splitmix64/fnv1a，微小差异即破坏一致。
- **危害**：跨语言跨端 hash 校验失败。
- **修复**：确定性算法只在中间件 C++ 实现一份，各端通过 C ABI 调用。
- **本仓现状**：⚠️ 中间件提供了 `_fnv1a_hash/_splitmix64_next`，但服务端又复制了用法，
  未走统一封装（见 C1）。

---

## C3 定点数/浮点混用

- **现象**：部分计算用定点数、部分用 float，跨端浮点精度不同导致结果漂移。
- **危害**：伤害/坐标跨端不一致。
- **修复**：所有跨端计算统一定点数。
- **本仓现状**：✅ 战斗用 `cabi.fp_*` 定点数，✅；但 `_roll_loot` 的数量/物品表未走统一（C1）。

---

## C4 随机数消耗顺序不一致

- **现象**：同一 seed，各端调用随机数的**顺序/次数**不同，即使算法相同结果也不同。
- **危害**：同 seed 产出漂移。
- **修复**：明确"谁先消费、消费几次"的调用契约，统一序列。
- **本仓现状**：⚠️ `_roll_loot` 随机消耗序列与中间件 `roll_loot` 完全不同（C1）。

---

## C5 时间/时钟依赖导致不一致

- **现象**：确定性逻辑混入 `time.time()/random.time()`，每次运行结果不同。
- **危害**：跨端/跨次不一致。
- **修复**：确定性计算禁用真实时钟，统一注入 seed/帧号。
- **本仓现状**：⚠️ `combat_id` 用 `time.time_ns()` 生成（非确定性，可接受，仅作 ID），
  但**战斗/掉落结果必须纯 seed 驱动**，已确认掉落走 seed（C1 待修）。

---

## C6 哈希/版本跨端未校验

- **现象**：生成结果未做跨端 SHA-256 一致性校验，漂移后无感知。
- **危害**：出问题不知哪端坏了。
- **修复**：各端产出结果统一 `hash_json` 校验，golden 比对。
- **本仓现状**：✅ 中间件有 `hash_json`，四端适配层有 golden hash 测试，良好。
