# D 并发与竞态坑点

> 危害等级：🟠 并发问题通常偶发、难复现，但一旦触发就丢数据/超发/幽灵覆盖，是最难排查的一类。
> **同一玩家/同一物品的并发写操作必须加锁或乐观锁。**

---

## <a name="D1"></a>D1 账本并发超发（双花）

- **现象**：玩家并发发起多笔扣款，`balance < amount` 检查非原子，两笔同时通过 → 余额为负超发。
- **危害**：货币双花，经济受损。
- **修复**：扣款用原子操作（`balance -= amount` 前先 `if balance >= amount` 在**同一锁/事务**内）；
  或加乐观锁版本号。
- **本仓现状**：⚠️ `debit` 的检查与扣减非原子，多线程/多请求并发下存在竞态窗口（服务为单进程内存态，
  单线程下暂安全，但无锁防护）。

---

## D2 战斗奖励重复发放（重放）

- **现象**：`process_attack` 攻击胜利后发奖，若客户端重发 victory 请求，重复发奖。
- **危害**：奖励刷取。
- **修复**：victory 发奖加幂等键（combat_id 已发过则跳过）。
- **本仓现状**：⚠️ 见 A4。`finished=True` 后 `process_attack` 会返回 error，✅ 部分防重，
  但网关层发奖逻辑可被构造请求重复触发（session 未清）。

---

## <a name="D3"></a>D3 任务进度并发覆盖（幽灵覆盖）

- **现象**：`_handle_quest` 直接 `cur["progress"] = progress` 覆盖，无单调递增校验。
  客户端并发上报或乱序上报，高进度被低进度覆盖，或反向刷进度。
- **危害**：任务进度错乱/作弊刷完成。
- **修复**：进度**只增不减**，且服务端校验只能单调增长；若为计费/奖励任务需服务端计算。
- **本仓现状**：⚠️ progress 直接覆盖，无单调校验；进度值也无上限校验（可传超大值刷 completed）。

---

## D4 采集/使用物品并发竞态

- **现象**：`collect`/`use_item` 读-改-写库存非原子，并发下丢失或双加。
- **危害**：物品超发/丢失。
- **修复**：库存操作加锁/乐观锁，服务端校验库存非负。
- **本仓现状**：⚠️ `world_state` 库存操作无锁，无负数校验。

---

## D5 快照版本并发混乱

- **现象**：`_deltas` 无限增长、版本号在并发下错乱，客户端增量同步乱序。
- **修复**：增量带版本号，客户端按版本消费；服务端定期清理已消费增量。
- **本仓现状**：⚠️ `_deltas` 有版本号 ✅，但无定期清理、`snapshot` 全量返回所有实体（超 SNAPSHOT_SIZE 约束）。
