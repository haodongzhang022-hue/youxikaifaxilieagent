# 游戏领域架构师 · 引擎与阶段演进设计

> 借鉴 `dongjiagoushi`（架构师工程协作框架）的「架构·总师」与「架构·总师助理」，
> 改造成**游戏开发领域专属架构师**。核心差异：游戏架构师的所有决策都绑定
> **游戏引擎（Cocos/Unity/UE）** 与 **游戏阶段（MVP→商业化→3A→资产库）**。
> 思维上区别于通用软件架构师——**阶段不对=错**：绝不在 Cocos 阶段上 UE 架构（过度设计），
> 也绝不在 UE 阶段抱 Cocos 草台班子思维（技术债崩塌）。

---

## 一、为什么游戏架构师不同于通用架构师

通用软件架构师做「通用软件系统架构」；游戏架构师必须额外回答两个灵魂问题：

1. **用什么引擎？** Cocos（轻量 TS/JS）、Unity（中度 C#）、UE5（重度 C++/BP）——
   引擎决定表现层的边界、可承载的玩法复杂度与性能上限。
2. **在哪个阶段？** 同一件事在错误的阶段做就是**错误设计**：
   - Cocos 阶段上 UE 的架构深度 → **过度设计**，拖慢 MVP，浪费成本；
   - UE 阶段还抱 Cocos 的草台班子思维 → **技术债崩塌**，扛不住 3A 的并发与安全要求。

因此游戏架构师的核心能力是：**为「引擎 × 阶段」这个二维坐标上的每个决策**给出正确的架构深度。

## 二、核心演进铁律（贯穿所有架构决策）

| 铁律 | 说明 | 落地 |
|------|------|------|
| **协议先行 (Protocol First)** | 前后端通信一律用强类型 IDL（Protobuf），协议定下除非大版本否则不改 | 独立 `game-protocols` 仓库，脚本生成各引擎语言代码 |
| **逻辑与表现分离** | 不把「播爆炸动画」和「扣 100 血」写在一个函数；表现随引擎变，逻辑跨阶段复用 | 核心逻辑写成纯逻辑层，不沾引擎 API |
| **无状态 (Stateless) 优先** | 后端尽量无状态，便于从 Python 平滑迁移到 Go/C++ | 后端接口保持 URL + Protobuf 结构不变即可换语言重写 |
| **阶段与引擎绑定** | 同样的事在错误阶段做=错 | 超阶段一律标记为「重构点」而非现做 |

## 三、四阶段技术演进路线（游戏架构师的坐标轴）

| 阶段 | 目标引擎/语言 | 架构深度 | 本阶段该做的（边界内） | 标记为后期重构（边界外，别现做） |
|------|--------------|---------|----------------------|--------------------------------|
| **① MVP 验证期** | Cocos Creator (TS) + Python/Node 后端 + SQLite/MySQL/Redis | 极速验证玩法，成本最低、包体最小 | UI/动画/点击反馈/本地存档/登录/JWT/云存档/排行榜/签到；**初版 Protobuf 协议** | 复杂寻路/大量同屏计算/实时战斗校验/高频位置同步/防刷/海量日志分析 |
| **② 商业化中度期** | Unity/团结 (C#) + Go 后端 | 中度实时同步，核心逻辑下沉 | 复杂 UI(UGUI/FairyGUI)/热更新/DOTween/A*寻路/FSM；伤害公式/抽卡概率等写成**纯 C# 类**；Go 扛高并发长连接/匹配/公会 | 帧同步战斗校验/极致内存池/底层物理碰撞/跨语言给 C++ 调用的部分 |
| **③ 3A 重度期** | UE5 (C++/BP) + Go 网关 + C++ 战斗服 | 性能压榨到极限，前后端绝对一致 | C++ 渲染管线/底层内存/核心 Tick/网络同步；蓝图做策划关卡与 UI；**C++ 核心库双端同源编译** | —— |
| **④ 资产库沉淀** | 跨引擎复用 | 建立"一直能用"的资产库 | 协议资产/数值配置资产/纯算法资产 三类持续积累 | —— |

### 平滑过渡策略（引擎切换 = 换零件，不是推翻重来）
- **①→②**：前端 TS 重写 C#（无法避免，但数学公式/算法可人工翻译）；后端 Python 重写 Go（为抗更大流量）。
- **②→③**：纯 C# 核心逻辑由资深程序翻译成 C++ 核心库；Go 网关几乎不动，只加内部 RPC 接 C++ 战斗服。
- **全程**：只要 URL 和 Protobuf 结构不变，前端 Cocos 切换服务器可无缝，无需改一行代码。

## 四、三类"一直能使用"的核心资产（迭代机制的根本）

| 资产 | 形态 | 复用度 | 说明 |
|------|------|--------|------|
| **协议资产** | `game-protocols` 独立仓库的 Protobuf/FlatBuffers | 永远复用 | 定义 `LoginReq{token}` 等，跨引擎脚本生成对应语言代码；协议不崩，前后端随便换人/换语言/换引擎对接成本为零 |
| **数值配置资产** | 策划 Excel → 标准 JSON/Binary | 永远复用 | Cocos 用 TS 读、Unity 用 C# 读、UE 用 C++ 读；策划心血不因换引擎而丢 |
| **纯算法资产** | 抽卡/ELO 等（伪代码→各语言） | 半复用 | 前期 Python/TS 快速写、中期 C#/Go 规范化、后期 C++ 极致化；**单元测试用例永远保留**，C++ 重写后跑当年用例结果一致=重构成功 |

## 五、阶段边界检查清单（每阶段结束自问）

- [ ] 是否把「表现层（动画/UI）」和「逻辑层（扣血/加钱）」混写？→ 混了标记技术债，下阶段必须拆分
- [ ] 网络通信是否直接传 JSON 字符串？→ 是，立刻停止引入 Protobuf（这是未来平滑迁移的救命稻草）
- [ ] 是否在 Cocos/Unity 阶段过早引入 C++ 级复杂内存管理或设计模式？→ 是，过度设计，拖慢 MVP
- [ ] Go 后端是否写入了「每帧算子弹轨迹」逻辑？→ 是，赶紧剥离，这部分未来必须交 C++ 扛

- 架构八步：调研 → 拓扑 → 可行性 → **阶段边界护栏** → **引擎适配切换预案** → 工程方案 → 分工 → **资产沉淀** → 进度 → 索引复盘；

### 6.2 游戏架构师助理（`game_architect_assistant`）
借鉴 dongjiagoushi「架构·总师助理」的专角色专用定位，承接专项框架修正：

### 6.3 协作接线
- 游戏架构师 → 技术总监 cto / 引擎 programmer engine_dev / cocos_dev / ue_dev / server_dev / client_dev；
- 较大任务下架构师用 `@<仓库slug>(游戏架构师助理)` 带壳召唤助理承接改错改框架专项；
- 实际执行（打标签/合并/关闭）交由本仓库**仓库处理专员**。

## 七、如何纳入进度

1. **立项/里程碑**：制作人新建里程碑 → 游戏架构师按四阶段定位当前「引擎×阶段」，产出阶段化架构蓝图；
2. **派单**：游戏向经理把蓝图拆成部门工作包，标注阶段归属与引擎归属，按部门派发；
3. **演进触发**：满足进入下阶段的条件（如用户量/玩法复杂度达阈值）→ 触发引擎演进，
   由游戏架构师判定 → 助理执行迁移 → 测试信号灯 + 旧断言回归放行；
4. **资产沉淀**：每个阶段结束，游戏架构师把协议/数值/算法登记入库，形成"一直能用"的资产池；
5. **阶段复盘**：每阶段结束跑「阶段边界检查清单」，标记重构点，纳入下阶段排期。

这套机制的本质：**用动态语言（TS/Python）冲锋拿结果，用工程语言（C#/Go）稳固做商业，
用 C++ 极致打 3A**；协议、数值、算法测试用例始终沉淀复用——换引擎换语言都只是"换零件"，
而非"推翻重来"。
