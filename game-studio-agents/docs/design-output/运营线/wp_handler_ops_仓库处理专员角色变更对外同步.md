## 一、背景与同步目标

PM `wp_handler_pm` 验收通过仓库处理专员职责边界与闭环：
- 仓库处理专员 = **本仓库唯一打标签执行者**（标签驱动，禁止 push）；
- 标签驱动闭环「修复→打标签→触发下一轮评审」完整可复现；
- 召唤优先级链（仓库处理专员→CodeBuddy 兜底）固化生效。

运营线负责将这一**角色变更**对外同步，确保外部协作方正确理解角色分工变化。

## 二、仓库处理专员角色变更对外影响范围（reference_learner）

### 2.1 变更概览

| 变更点 | 变更前 | 变更后 |
|--------|--------|--------|
| 打标签执行者 | 多角色可打标签 | **仓库处理专员**唯一执行 |
| 打标签驱动 | 无明确闭环 | 修复→打「适合推送」→触发下一轮评审 |
| 召唤优先级 | 裸 @CodeBuddy | **仓库处理专员 → CodeBuddy** 逐个降级 |
| 推送机制 | 依赖 push 事件 | **无 push 依赖**，全程标签驱动 |

### 2.2 需要同步的文档清单（reference_learner）

| 文档/渠道 | 变更内容 |
|-----------|---------|
| 内部开发文档 | 角色清单新增仓库处理专员，明确打标签唯一执行者 |
| 协作流程文档 | 打标签流程改为召唤仓库处理专员，不再自建 |
| 外部协作手册 | 说明打标签操作需通过仓库处理专员完成 |
| CI 配置文档 | 更新标签驱动闭环说明（适合推送/合并/关闭） |

## 三、对外同步说明（game_operator）

### 3.1 对外沟通策略

| 沟通对象 | 同步内容 | 优先级 |
|---------|---------|--------|
| 内部团队 | 角色变更说明、打标签流程调整 | P0 |
| 发行/渠道 | 代码提交与合入流程不变，标签状态作为推进信号 | P1 |
| 玩家社区 | 内部机制不对外公开，无需用户侧同步 | P2 |

### 3.2 对外沟通话术模板

> **对内**：仓库处理专员为打标签唯一执行者。发现需打标签的场景，请召唤仓库处理专员处理。
> 闭环流程为「修复 → 打标签 → 触发下一轮评审」，全程标签驱动，无需 push。
>
> **对外（如需）**：项目代码协作流程已优化为标签驱动闭环，提交/合入进度以标签状态为准。
