## 一、核心思想：阶段不对就算错

游戏玩法/系统架构与通用软件不同：**每个玩法模块必须绑定「引擎 × 阶段」二维坐标**。
- Cocos 阶段（MVP）做 UE 的复杂玩法 = **过度设计**，拖慢验证速度。
- UE 阶段（3A）还抱着 Cocos 的草台玩法 = **技术债崩塌**。

因此，玩法系统设计必须给出**四阶段边界矩阵**，明确"本阶段应做"与"标记后期重构"。

## 二、四阶段玩法/系统架构边界矩阵

| 玩法/系统 | 阶段1 Cocos/MVP | 阶段2 Unity/商业化 | 阶段3 UE/3A | 阶段4 资产库 |
|-----------|----------------|-------------------|-------------|-------------|
| 核心循环 | 单局快速循环（点击/轻操作） | 数值养成+活动循环 | 开放大世界+硬核实时 | 循环规则抽象 |
| 战斗玩法 | 简单回合/自动战斗 | 即时/半即时、技能组合 | 帧同步硬核对战 | 战斗规则协议化 |
| 关卡 | 线性少量关卡 | 章节+难度梯度 | 大世界/副本 | 关卡配置表资产 |
| 社交 | 好友+排行榜 | 公会+组队+聊天 | 跨服/阵营 | 社交协议资产 |
| 经济 | 单一货币 | 多货币+商城 | 复杂经济+跨服 | 经济规则资产 |

## 三、阶段边界护栏（越界即打回）

```python
# 示例：Cocos 阶段检查（对应 config/stage_aware_engine.py）
guard.check('open_world_map', GameStage.STAGE1_COCOS)
# -> 命中"边界外"：Cocos 阶段不该做开放大世界，标记为后期重构
```

**越界护栏清单**：
- [ ] 本阶段是否引入了远超本阶段目标（MVP/商业化/3A）的玩法复杂度？
- [ ] 是否把"表现层交互"与"玩法逻辑"混在一起写？（逻辑与表现分离）
- [ ] 玩法事件是否直接传 JSON？应使用结构化协议（协议先行）
- [ ] 是否过早引入 UE 阶段才需要的复杂度？

## 四、引擎无关分层（对齐程序线 wp_client 纯逻辑层）

```
玩法逻辑层（Engine-Agnostic）：核心循环/规则引擎/状态机 —— 跨引擎复用
        ↕ IEngineAdapter 事件映射
引擎表现层：Cocos / Unity / UE 各自适配器 —— 随引擎更换整体替换
```

## 五、跨阶段复用资产

1. **玩法规则协议**：事件/指令结构化定义，不依赖引擎类型。
2. **核心循环状态机**：逻辑层纯抽象，跨引擎保持一致。
3. **重构点标记**：每个"标记后期重构"的模块都有明确归属阶段。
