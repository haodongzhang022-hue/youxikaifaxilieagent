# 统一管理与可视化指挥中枢（Unified Command Center）

> 本文档为"游戏开发系列 Agent"设计一个**统一的管理和可视化页面**——指挥中枢。
> 它不是把所有信息平铺给用户，而是以**信息论视角**对多 Agent 协同产生的海量事件
> 做**降熵（缩减信息熵）**处理：原始基础信息全程可溯源、可钻取，但默认只展示
> **聚类聚合后**的关键信息与判断信息，并以**渐进式**方式展开，让用户在**拿到足够
> 支撑决策的信息**（而非靠猜测）与**不被噪音淹没**之间取得平衡。

---

## 〇、设计目标与信息论定位

### 为什么需要指挥中枢

多 Agent 协同（游戏向经理 → 六大部门 → 调度器 → 消息总线）会产生**海量、零散、
高频**的事件流：派单、依赖解锁、验收、打回、返工、评审、合并……每一件都可溯源，
但如果全部平铺，就会形成**高信息熵的噪音**，用户（制作人/PM/开发者）无法快速判断
"现在到底卡在哪、要不要我介入、下一步是什么"。

指挥中枢的核心价值是**降熵**：

| 信息论指标 | 原始状态（无中枢） | 指挥中枢处理后 |
|-----------|-------------------|---------------|
| 信息量（H） | 高熵：海量事件平铺 | 降熵：聚合为"关键信息 + 判断信息" |
| 信噪比 | 低：有效信号被噪音淹没 | 高：噪音折叠进可钻取的溯源层 |
| 可决策性 | 低：信息不足/过载，靠猜 | 高：提供足以判断的上下文 |
| 可溯源性 | 有（但散落） | 高：任何结论可下钻到底层原始事件 |

### 三大原则

1. **可溯源（Sourceable）**：每条聚合结论都可下钻到原始基础信息，绝不丢失证据链。
2. **渐进式（Progressive）**：默认只展示必要层，按需逐级展开，避免一次性信息过载。
3. **可决策（Decidable）**：对"关键判断"给出足够支撑的信息，杜绝"信息不足靠猜"。

## 一、信息分层模型（降熵的核心）

把信息按"抽象程度"分为四层，自上而下抽象度递减、信息量递增。**默认只看第一层**，
需要时逐级下钻，形成"总览 → 聚合 → 明细 → 原始"的渐进式展开。

```
L0  总览层（Executive）        —— 一眼看懂全局，支撑"要不要介入"的决策
│     关键数字/健康度/风险信号/阶段进度
▼
L1  聚合层（Aggregate）        —— 聚类分类后的关键信息与判断信息
│     工作包分组/依赖拓扑/风险聚类/判断结论
▼
L2  明细层（Detail）           —— 单个实体的结构化信息
│     单个工作包状态/单部门产出/单次验收记录
▼
L3  原始层（Raw/Source）       —— 可溯源的原始基础信息
     事件流/日志/原始消息/提交记录/评审原文
```

### 各层信息构成

| 层 | 信息内容 | 默认可见 | 消费对象 |
|----|---------|:-------:|---------|
| **L0 总览** | 全局健康度、阶段进度、风险信号、关键指标 | ✅ 首屏 | 制作人/PM 快速决策 |
| **L1 聚合** | 部门聚类、依赖拓扑、风险聚类、判断信息 | ✅ 分页内 | 项目经理/部门负责人 |
| **L2 明细** | 单个工作包/产出/验收的完整结构化信息 | 🔽 点击展开 | 部门负责人/执行者 |
| **L3 原始** | 事件流、日志、消息、提交、评审原文 | 🔽 下钻溯源 | 开发/审计/排障 |

## 二、功能分页设计

指挥中枢采用**功能分页**，每个分页对应一类管理场景，同一套信息分层模型贯穿始终。

```
┌──────────────────────────────────────────────────────────────┐
│  游戏开发指挥中枢                                          [角色] │
├─────────┬──────────┬──────────┬──────────┬──────────┬─────────┤
│ 全局总览 │ 工作包看板 │ 部门协作 │ 风险与阻塞 │ 事件溯源 │ 决策台账 │
├─────────┴──────────┴──────────┴──────────┴──────────┴─────────┤
│  ┌─ L0 总览卡（每页顶部常驻，展示本页关键信号）─┐               │
│  │  健康度 / 进行中 / 阻塞中 / 风险数 / 进度    │               │
│  └──────────────────────────────────────────────┘               │
│  本页主体内容（按需聚合 / 明细 / 下钻溯源）                      │
└──────────────────────────────────────────────────────────────────┘
```

| 分页 | 核心问题（决策视角） | L0→L3 落点 |
|------|--------------------|-----------|
| **全局总览** | "整体健康吗？要不要我介入？" | 健康度雷达、阶段进度条、风险信号 |
| **工作包看板** | "哪些在推进、哪些卡住了？" | 看板列、工作包卡、点开见明细 |
| **部门协作** | "部门间依赖顺畅吗？谁在等谁？" | 依赖拓扑图、上下游解锁链路 |
| **风险与阻塞** | "有什么会拖期？该给谁派返工？" | 风险聚类、阻塞清单、打回记录 |
| **事件溯源** | "某个结论的原始证据是什么？" | 事件流、日志、消息、提交、评审 |
| **决策台账** | "以前怎么判的？这次依据够吗？" | 判断信息、依据链、置信度 |

> 每个分页解决一个"决策问题"，并让用户能在该页内逐级下钻拿到足够判断的信息。

## 三、信息熵缩减策略（降熵的具体手法）

在每一层都执行"聚类 → 折叠 → 摘要"，把高熵事件流压缩为低熵关键信息。

### 3.1 聚类（Clustering）

按**业务维度**把海量事件/实体聚成类：

- **按部门聚类**：策划/程序/美术/测试/项目管理/运营
- **按状态聚类**：进行中 / 已验收 / 阻塞中 / 待返工 / 待派发
- **按风险聚类**：延期风险 / 依赖风险 / 质量风险 / 资源风险
- **按模块聚类**：玩法 / 客户端 / 服务端 / AI / 美术 / 测试 / 发版 / 运营

聚类结果为"组 + 关键数字 + 代表实体"，而非罗列每个实体。

### 3.2 折叠（Folding）

聚合后，把**可下钻的细节折叠起来**，只在需要时展开：

```
▸ 程序线 · 4 个工作包 · 2 进行中 / 1 阻塞 / 1 待派发     ← 折叠态（L1）
    ▸ 客户端渲染与交互 (client)  · 阻塞中 · 依赖 gameplay  ← 展开（L2）
        ▸ [事件] REVIEW_RESULT 打回: 设计不完整           ← 溯源（L3）
```

### 3.3 摘要（Summarization）

对连续事件流生成**一句话摘要 + 判断结论**，替代逐条展示：

- 原始：15 条派单/解锁/验收事件
- 摘要：`程序线已解锁，2/3 依赖就绪，等待美术资源验收`
- 判断：`下游发版存在 1 项延期风险，建议优先派单给美术线`

## 四、关键信息与判断信息的生成（决策支撑）

### 4.1 关键信息（Signal）

从原始事件中抽取**影响决策的信号**，而非展示全部事件：

| 信号类型 | 提取方式 | 示例 |
|---------|---------|------|
| 进度信号 | 完成/总数、剩余关键路径 | `发版依赖链完成度 60%` |
| 健康信号 | 阻塞数、返工率、验收通过率 | `本周验收通过率 80%` |
| 风险信号 | 依赖未解锁、DDL 临近、反复打回 | `美术资源反复打回 3 次` |
| 资源信号 | 部门负载、关键角色占用 | `程序线主责角色负载 120%` |

### 4.2 判断信息（Judgment）

在关键信息之上，给出**有依据的判断**，并**显式标注依据链与置信度**，
确保用户"拿到足够信息做决策，而非靠猜测"：

```
⚠️ 判断：发版阶段存在延期风险
   依据链：
     · 发版依赖 4 个下游工作包，其中 2 个仍阻塞
     · 美术资源已反复打回 3 次（最近一次: REVIEW_RESULT/未达验收标准）
     · 关键路径上 DDL 剩余 2 天
   置信度：高（三路信号一致）
   建议动作：派返工给美术线 lead_designer，或调整发版里程碑
```

> **判断必须可溯源**：每个判断列出"依据链 + 置信度"，用户可一键下钻到 L2/L3
> 核实原始证据，避免"拍脑袋"或"信息不足靠猜"。

## 五、渐进式展开（Progressive Disclosure）交互范式

统一交互范式：**默认折叠 → 按需展开 → 深层溯源**。

```
首屏（L0）              →  只展示 5~7 个关键数字 + 健康度 + 风险信号
点击聚合卡（L1）        →  展开该聚类的分组明细与判断信息
点击单个实体（L2）      →  查看完整结构化信息
点击"溯源"（L3）       →  下钻到原始事件流/日志/消息原文
```

**展开原则**：

1. **一次只展开一层**，避免直接跳到原始层造成过载；
2. **每层都带"退出/收起"**，随时回到上一层；
3. **展开有代价提示**：如需加载大量原始事件，先显示摘要与条目数；
4. **决策路径最短**：对"要不要介入/派谁返工"这类高频决策，把关键判断直接放首屏。

## 六、数据结构与后端支撑

指挥中枢的数据来自多 Agent 协同系统的已有产出，需为其建立**统一可查询的数据视图**。

### 6.1 数据源

| 数据源 | 对应实体 | 说明 |
|--------|---------|------|
| `game_producer_agent.py` | 工作包、部门、依赖、验收 | 编排主数据 |
| `task_scheduler.py` | 任务状态、依赖解锁 | 推进状态 |
| `message_bus.py` | 事件流（派单/通知/验收） | 溯源证据 |
| `.cnb.yml` 流水线 | CI 状态、评审、合并 | 流程证据 |
| `roles.yaml` | 部门/角色/能力 | 静态基线 |

### 6.2 建议的聚合接口（供可视化层调用）

```
GET /dashboard/overview          → L0 总览（健康度/进度/风险信号）
GET /dashboard/workpackages      → L1 工作包聚合（按部门/状态聚类）
GET /dashboard/dependencies      → L1 部门依赖拓扑
GET /dashboard/risks             → L1 风险聚类 + 判断信息
GET /dashboard/workpackages/:id  → L2 单个工作包明细
GET /dashboard/events?filters=   → L3 原始事件流（可溯源）
```

> 每个接口返回结构统一为 `{ meta(聚合摘要), items(明细), source(溯源指针) }`，
> 让前端天然支持"聚合 → 明细 → 溯源"的渐进式展开。

### 6.3 数据模型示例（工作包）

```python
work_package = {
  "id": "wp_client",
  "label": "客户端渲染与交互",
  "department": "program",
  "status": "blocked",                 # pending/active/done/blocked
  "deps": ["wp_gameplay"],             # 依赖
  "owner": "cto",
  "risk": {"level": "high", "reasons": ["rework_3x", "ddl_close"]},
  "judgment": {                        # 判断信息（决策支撑）
    "conclusion": "发版存在延期风险",
    "evidence_chain": ["REVIEW_RESULT/未达验收标准", "deps_unlocked=2/4", "ddl_remaining=2d"],
    "confidence": "high",
    "suggested_action": "派返工给美术线 lead_designer"
  },
  "source_events": ["event_1023", "event_1041"]   # 溯源指针 → L3
}
```

## 七、与现有系统的对接

指挥中枢**不改变**现有"机制驱动、非手动推进"的协同方式，只在其上叠加**可视化与决策层**：

| 现有组件 | 对接方式 |
|---------|---------|
| 消息总线 `message_bus` | 事件流作为 L3 溯源数据源，按业务维度建立索引 |
| 任务调度器 `task_scheduler` | 任务状态实时映射到看板/依赖拓扑 |
| 游戏向经理 `game_producer_agent` | 工作包/验收/风险判断作为 L1/L2 主数据 |
| `.cnb.yml` 流水线 | CI 状态/评审/合并作为决策证据并入 L3 |

**演进路线**：

| 阶段 | 内容 | 状态 |
|------|------|------|
| v0.7 | 多部门 Agent 端到端联动跑通全流程 | 🔜 前置 |
| v0.8 | 接入回转/打断协议 + 经验记忆库 | 🔜 |
| **v0.9** | **指挥中枢：信息分层模型 + 降熵聚合接口（本设计）** | 🔜 本方案 |
| v1.0 | 指挥中枢前端：功能分页 + 渐进式展开可视化 | 🔜 |

## 八、验收标准

指挥中枢上线后，应能回答以下"决策问题"，且**每一步都能下钻溯源**：

| # | 决策问题 | 指挥中枢的回答 |
|---|---------|---------------|
| 1 | 整体健康吗？ | L0 健康度 + 风险信号（一眼可见） |
| 2 | 现在卡在哪？ | L0 阻塞信号 → L1 阻塞聚类 → L2 明细 |
| 3 | 该不该我介入？ | L0 判断信息 + 置信度 + 依据链 |
| 4 | 给谁派返工？ | L1 风险聚类 + 判断信息（建议动作） |
| 5 | 证据是什么？ | L3 原始事件/日志/消息一键溯源 |
| 6 | 以前怎么判的？ | 决策台账（经验记忆库） |

> 信息论检验：指挥中枢应做到——**用户无需看全部事件也能做对决策（降熵），
> 且想看任何一条判断的原始依据都能找到（可溯源）**。
