# 05. 端到端工作流与示例

用一条完整示例串起"能力、行为逻辑、触发时机、Mod 规范"四份文档。

## 场景示例：借鉴《某开放世界生存游戏》的"建造循环"

### 第 1 步：触发（Trigger）

- 触发类型：**指令触发**（用户显式提出）+ **数据触发**（自有游戏发现玩家中期留存下滑）。
- 触发信号：*"参考《某开放世界生存游戏》的建造系统，改善我们中期的建造体验。"*
- 进入 `INPUT_PENDING`，注入上下文（基线版本、知识库检索结果、策略配置）。

### 第 2 步：准入（Gate）

- 知识库检索 → 无重复借鉴 → 通过。
- 素材完备（有视频+设计文档）→ 通过。
- 契合初筛（同为生存建造品类）→ 通过，进入分析。

### 第 3 步：理解层 L1（Analysis）

Agent 产出《机制分析报告》：
- **核心循环**：采集资源 → 解锁蓝图 → 建造设施 → 扩展生存范围 → 面对更高威胁。
- **系统拆解**：资源系统、蓝图/科技树、建造摆放系统、威胁压力系统、家园成长系统。
- **数值模型**：资源产出速率 vs 建造消耗曲线；中期"建造目标感"建立节奏。
- **心智模型**：通过"阶段性目标 + 进度可见性"维持心流与成就感。

### 第 4 步：迁移层 L2（Assess）

- **契合度评分**：82 分（高）。
- 取舍矩阵：
  - `keep`（整体搬）：蓝图解锁带来的"渐进目标感"。
  - `adapt`（需改造）：资源产出曲线——我方节奏更快，需微调消耗倍率。
  - `trim`（需裁剪）：过于复杂的建造碰撞体系统，简化。
  - `drop`（放弃）：高威胁压力系统（与休闲向定位不符）。
- **创新点**：将"蓝图解锁"与自有"家园装饰系统"结合，形成"建造 = 生存 + 个性化"双驱动。
- **风险**：机制借鉴不涉及版权保护的美术/代码直拷，合规。

### 第 5 步：决策（Decide）

生成决策单（格式见 `02`），结论：**值得落地，聚焦"中期建造目标感"单一借鉴点**。

### 第 6 步：落地层 L3（Build Mod）

按 Mod 规范生成模组 `mod/build-progression`：
- `scope: [feature, presentation, visual]`
- `feature/logic/`：蓝图解锁逻辑、资源消耗倍率配置。
- `presentation/hud.yaml`：增加"下一个建造目标"进度条。
- `visual/ui/`：目标达成时的视觉反馈动效。
- `manifest.yaml` 声明 `enabledByDefault: false`、`rollbackPoint`、`safeToggle: true`。

### 第 7 步：沙盒验证（Sandbox Verify）

在隔离环境加载 Mod，验证：
- 蓝图解锁逻辑正确，无越权修改基线。
- 运行时开关 `enabled/disabled` 不破坏存档。
- 一键回滚到基线成功。
- 通过 → 进入审核。

### 第 8 步：审核与合入（Review & Commit）

- 因默认能力为 L2，产出供人工审核，合入主分支前需 approved。
- 通过后发布，Mod 可启用。

### 第 9 步：归档与记忆（Archive）

- 决策单、分析报告、Mod 全部回写仓库知识库。
- 后续类似借鉴直接检索复用，保持风格一致。

## 端到端时序图

```
用户 ──触发──▶ Agent(Gate) ──▶ Analysis ──▶ Assess ──▶ Decide
   ▲                                                      │
   │                                                      ▼
   │                                                  Build Mod
   │                                                      │
   │                                                      ▼
   │                                                Sandbox Verify
   │                                                      │ 通过
   │                                                      ▼
   │                                             Review & Commit
   │                                                      │
   └────────────── 归档知识库 ◀─────────────────────────────┘
```

## 验收标准

一条借鉴从触发到落地，应满足：

1. 产出结构化决策单（含分析/评分/取舍/风险）。
2. 落地改动以 Mod 形式交付，可开关、可回滚。
3. 沙盒验证通过且人工审核（L2）后才发布。
4. 全过程归档回知识库，形成可复用资产。

## 补充示例：探索多模式 + 相似度校准（校验/校准机制演示）

**诉求**：*"参考《某开放世界生存游戏》的建造循环，但只学它的**玩法结构**，美术要完全自有风格，避免抄成一样。"*

### ① 校验：探索模式决策（docs/09）

进入分析前，`reference_learner` 先做探索模式决策：

```
request: "参考建造循环，只学玩法结构，美术要自有，避免抄一样"
→ 模式: gameplay_loop（默认）
→ 渠道广度: multi（官方+实机+拆解贴）
→ 信息类型: [video, motion, numeric, mindset]   # 不纳入 art，避免美术干扰
→ 深度: dig
→ anti_targets: ["美术照搬"]                      # 明确反参考点
```

只采集声明的渠道与类型，产出**不含美术**的分析报告。

### ② 校准：相似度控制（docs/10）

落地前用 `CalibrationEngine` 检测相似度并控档：

```
目标档位: code_only 或 high（visual 不强约束）
第1轮实测: mechanics=0.88, visual=0.72, code=0.62
→ visual 偏高 → 调整指令: decouple（美术改为自有风格）
→ mechanics 偏高 → 调整指令: trim（裁剪 2 个子系统差异化）
第2轮: mechanics=0.71, visual=0.30, code=0.66 → 达标 stable
```

多轮迭代后，相似度进入目标档位容差带，才进入落地；若 3 轮仍未达标，保留最佳轮次并上报人工。
