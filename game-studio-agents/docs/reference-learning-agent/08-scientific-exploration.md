# 08. 科研探索能力（Scientific Exploration Capabilities）

> 在思维模式路由之上，为 `reference_learner` 引入**科研探索引擎**：
> 元学习、树探索、假设求证思维链、多 Agent 博弈。
> 目标是让借鉴从"照搬玩法"升级为"像研究者一样求证、像棋手一样推演、像评审团一样博弈"。

## 1. 四大科研能力总览

| 能力 | 一句话 | 解决的痛点 |
|---|---|---|
| **元学习**（Meta-learning） | 从"如何借鉴"中学习，迭代借鉴策略 | 每次借鉴评估标准不统一、越借越"手抖" |
| **树探索**（Tree Search） | 借鉴决策分叉成树，多分支并行推演 + 剪枝 | 单一决策路径容易漏掉更优落地方案 |
| **假设求证思维链**（Hypothesis-Verify CoT） | 先提假设 → 收集证据 → 验证/推翻 → 收敛 | 凭直觉借鉴，缺乏证据支撑 |
| **多 Agent 博弈**（Multi-agent Debate） | 不同思维链 Agent 辩论、评审、投票 | 单一视角决策，盲区多 |

## 2. 元学习（Meta-learning）

**核心思想**：Agent 不仅"学借鉴内容"，更"学如何借鉴"。每次借鉴结束，反思自己的评估过程，
并迭代"借鉴策略"（评估标准、阈值、取舍规则）。

### 2.1 元学习回路

```
借鉴结束 → 复盘本次决策 → 提取"评估是否准确" → 调整策略参数 → 写入元知识库
```

### 2.2 元学习产出物（策略卡）

```yaml
meta_learning:
  session_id: <本次借鉴ID>
  reflection:
    - "本次契合度评分(82)与最终玩家反馈(好评率68%)偏差较大"
    - "原因: 高估了'战斗深度'维度权重，低估了'上手门槛'"
  strategy_updates:
    - {key: "fit_weights.battle_depth", from: 0.4, to: 0.25, reason: "实证反馈"}
    - {key: "fit_weights.learning_curve", from: 0.2, to: 0.35, reason: "实证反馈"}
  next_apply: "后续适配评估采用更新后的权重"
```

### 2.3 实现要点

- 元知识库独立于借鉴知识库（前者存"如何评估"，后者存"评估了什么"）。
- 策略更新需**人工审核**后才全局生效（L2），避免单一案例过度拟合。

## 3. 树探索（Tree Search）

**核心思想**：对一个借鉴机制，不只给出单一落地方案，而是**分叉成多分支推演**，
每个分支评估收益/成本/风险，按置信度剪枝，最终收敛到最优分支或保留备选。

### 3.1 树探索流程

```
根节点: 借鉴机制 M 应如何落地？
 ├── 分支 A: 整体搬（keep）        → 收益高 / 成本高 / 风险中
 ├── 分支 B: 裁剪后搬（trim）      → 收益中 / 成本中 / 风险低
 ├── 分支 C: 改造融合（adapt）     → 收益中 / 成本高 / 风险低
 └── 分支 D: 放弃（drop）         → 收益零 / 成本零 / 风险零
        ↓ 每分支评估
        子分支: 若走分支 B，具体裁剪哪些元素？再分叉...
        ↓ 按评分排序 + 剪枝
最终: 推荐 Top1 分支 + 保留 Top2 备选
```

### 3.2 树探索产出物（探索树）

```yaml
tree_search:
  root_question: "借鉴机制M如何落地"
  branches:
    - {id: B, label: "trim", score: 86, reason: "...", sub_branches: [...]}
    - {id: A, label: "keep", score: 72, reason: "...", pruned: true, why: "成本超预算"}
  recommended: {branch: B, backup: C}
  depth: 2   # 探索深度
  confidence: 0.83
```

### 3.3 实现要点

- 借鉴论文的"路径承诺"：主分支一旦选定，后续聚焦执行，备选分支归档待用。
- 树探索默认深度 1-2（避免发散），复杂机制可加深到 3。

## 4. 假设求证思维链（Hypothesis-Verification CoT）

**核心思想**：每个借鉴决策不再"直接下结论"，而是先提**可证伪假设**，再用证据求证。

### 4.1 思维链模板

```
对借鉴点 X，我假设：
  H1: X 与自有游戏契合（因为……）
  H2: X 与自有游戏不契合（因为……）

收集证据：
  E1: 同类游戏 X 的玩家留存数据 → 支持 H1
  E2: 自有游戏目标玩家的偏好调研 → 支持 H1
  E3: 技术栈能否支撑 X 的实时反馈 → 反对 H2

验证：
  H1 得证（证据 E1+E2 支持，E3 无碍）→ 采纳 H1，走向落地
  H2 证据不足 → 推翻 H2

收敛结论: 采纳 X，以裁剪形式落地
```

### 4.2 证据来源（与 01-capabilities 的输入源对接）

| 证据类型 | 来源 |
|---|---|
| 玩家反馈 | 社区讨论、应用商店评论、玩家调研 |
| 数据 | 运营留存/流失、参与度、付费数据（对接 data_analyst） |
| 竞品 | 同品类游戏实况、设计复盘、数值表 |
| 技术 | 自有引擎能力、客户端/服务端可行性（对接 client_dev/server_dev） |

### 4.3 实现要点

- 每个假设必须有"证据"支撑，"无证据的结论"标记为低置信度。
- 契合度评分 = 证据支持度加权，而非凭感觉打分。

## 5. 多 Agent 博弈（Multi-agent Debate）

**核心思想**：用**不同思维模式 / 不同 persona 的多个 Agent** 对同一借鉴决策进行
辩论、评审、投票，避免单一视角的盲区。这是 dsh-router-standard
`dev_mode_subagent`（模式隔离子代理）的自然延伸。

### 5.1 博弈结构

```
借鉴决策 D 提交评审 →
 ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
 │  辩手 Agent  │  │  评审 Agent  │  │  怀疑者 Agent │
 │  (react 模式) │  │  (spec 模式) │  │  (weak 模式) │
 │  主张落地，列  │  │  评估可行性、 │  │  质疑风险、  │
 │  收益与亮点   │  │  计划与结构   │  │  找反例/漏洞  │
 └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
        └───────────────┼───────────────┘
                        ▼
              ┌─────────────────┐
              │  仲裁 Agent      │
              │ (spec, 聚合)     │
              │ 加权综合三方意见  │
              │ → 决策 + 置信度   │
              └─────────────────┘
```

### 5.2 角色与 persona（基于 dsh-router-standard 三波段）

| Agent 角色 | 思维模式 | Persona | 职责 |
|---|---|---|---|
| 辩手（Advocate） | **react** | 执行者，直接产出 | 论证"值得落地"，列出收益、亮点、实现路径 |
| 评审（Reviewer） | **spec** | 计划-集体，读优先 | 评估可行性、结构完整性、与路线图契合 |
| 怀疑者（Skeptic） | **weak** | 中性 + 分类 | 找风险、反例、边界情况、合规漏洞 |
| 仲裁（Arbiter） | **spec** | 计划-集体，聚合 | 加权综合三方，产出最终决策与置信度 |

### 5.3 博弈产出物（决策评审单）

```yaml
debate:
  decision: <D>
  participants:
    - {role: advocate, mode: react, verdict: "支持", weight: 0.3, key_points: [...]}
    - {role: reviewer, mode: spec, verdict: "有条件支持", weight: 0.3, key_points: [...]}
    - {role: skeptic, mode: weak, verdict: "反对", weight: 0.2, key_points: [...]}
  arbiter:
    - {verdict: "有条件支持", confidence: 0.78, conditions: ["需先验证X", "裁剪Y元素"]}
  action: "以裁剪形式落地，附加2个验证条件"
```

### 5.4 关键规则

- **模式隔离**：每个博弈 Agent 在自己的隔离上下文跑（fresh system prompt），
  避免相互污染（论文：会话中切换 persona 会失效前缀缓存）。
- **视角互补**：辩手(reactive) 与 评审/怀疑者(spec) 天然形成"产出 vs 审视"张力。
- **仲裁加权**：默认权重 辩手0.3 / 评审0.3 / 怀疑者0.2，可调；高风险决策加大怀疑者权重。
- **人机共治**：最终决策仍需人工确认（L2），博弈结果作为"决策依据"而非"代替人类"。

## 6. 科研引擎与既有状态机的融合

科研能力不改变既有状态机，而是在各阶段内部增强决策质量：

| 状态 | 科研增强 |
|---|---|
| ANALYSIS | 假设求证 CoT 引导机制拆解与数值还原 |
| ASSESS | 树探索多分支评估 + 元学习权重 |
| DECIDE | 多 Agent 博弈评审 + 树探索剪枝收敛 |
| BUILD_MOD | react 模式（routing 07）直接落地 |
| REVIEW_COMMIT | 博弈三方评审结果作为审核依据 |

## 7. 落地实现：`config/agent_boost/research_engine.py`

见配套文件，实现：元学习策略卡管理、树探索骨架、假设求证 CoT 模板、多 Agent 博弈编排。

## 8. 与思维模式路由的关系

- 科研引擎决定"**探究多深、怎么求证、谁来做评审**"。
- 思维模式路由决定"**用什么思维模式做**"（每个子 agent 落到 spec/react/weak）。
- 两者叠加：**正确的思维模式 × 充分的科研探索 = 借鉴上限的最大化**。
