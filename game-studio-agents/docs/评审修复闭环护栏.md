# 评审-修复闭环护栏（Review-Fix Loop Guardrail）

> 运行规范，确保「CL/OCI 评审返回问题 → 本仓库处理专员自动修复」这个闭环
> **稳定生效、有上限、不陷入无限循环**，并**多源触发、按场景分**。回应团队提出的机制改进方向。

## ⭐ 仓库处理专员（Repository Handler）说明

> **每个仓库都应默认有一个「仓库处理专员」**，是本仓库的**唯一执行者**。
> 它是**打标签的唯一执行者**，其他 agent 只有提供信息和建议的权利。

### 角色定义

「仓库处理专员」是**本仓库专属**的综合处理角色，集以下能力于一体：

1. **打标签（唯一执行者）**：本仓库所有打标签操作只能由仓库处理专员执行，
   其他角色（CodeBuddy / 代码审查员 / 游戏向经理 / 各线部门）只提供信息和建议；
2. **代码修复**：评审发现问题时负责修复代码并补测试断言；
3. **掌握本仓库完整带壳召唤格式**：`@<当前仓库slug>(角色名)`，其中角色名可以是
   `CodeBuddy` / `仓库处理专员` / `代码审查员` / `游戏向经理` 等；
4. **提供协作管线 MCP**：告知调用者本仓库的机制驱动流水线链路
   （Issue 新建 → 游戏向经理拆解 → 部门派发 → PR 评审 → 修复 → 合并 → 解锁下游）；
5. **提供目录索引**：告知关键配置文件位置（`.cnb.yml` / `.cnb/settings.yml` /
   `agent_identity.py` / `roles.yaml` / `game_producer_agent.py` / 测试信号灯等）；
6. **纠正错误调用**：当被裸 @ 或被路由到错误仓库时，明确给出正确的带壳调用方式；
7. **防止无效空转**：通过提供准确的信息，帮助调用者快速定位问题，节省 token 消耗。

### 打标签唯一执行者

**只有「仓库处理专员」可以执行打标签操作**（如「适合推送」「适合合并」「适合关闭」）。
其他所有角色（包括 CodeBuddy / 代码审查员 / 游戏向经理 / 部门 NPC）：
- **只提供信息和建议**，不执行打标签；
- 需要打标签时，必须召唤本仓库仓库处理专员（`@<当前仓库slug>(仓库处理专员)`）处理；
- 本仓库未部署仓库处理专员时，触发克隆一份到对应仓库后再用。

### 角色配置位置

- 角色定义：`.cnb/settings.yml` → `npc.roles` → `仓库处理专员`
- 身份自适应：`game-studio-agents/config/agent_identity.py` → `KNOWN_ROLES` 含「仓库处理专员」
- 召唤格式生成：`get_handler_mention()` → `@<slug>(仓库处理专员)`

### 如何召唤


> 裸 @ 会命中系统级或他仓 NPC，权限错位、内容对不上、无效空转。

## 〇、多源触发，按场景分（回应：触发信号不应只支持一种）

> 触发信号不是只能支持一种的——**允许不同源的触发方式而不是互相替换，都兼容才是对的**。
> 每种触发源覆盖不同场景，并存互补，各取所长：

| 触发源（.cnb.yml 事件） | 适用场景 | 作用 |
|------------------------|---------|------|
| **`pull_request`（主闭环 / 方案 A）** | 仓库处理专员修复后自动重跑（修完必**打标签**） | 最核心触发源：`测试信号灯 → 评审 → @仓库处理专员就地修复并打标签 → 触发新一轮 pull_request`，形成天然多轮循环；**钩子没 bug 就停**（评审通过即不再改）。仓库处理专员与本仓库 CodeBuddy 并存互补，优先仓库处理专员，CodeBuddy 兜底。**本系统故意设计不允许 push**。 |
| **`pull_request.changes_requested`** | 人工评审者以 git「需要改进」形式打回 | 兼容人工 git 级打回，与主闭环并存。 |
| **`pull_request.comment@npc`** | 人类主动 @仓库处理专员 / @CodeBuddy；评审 NPC 评审后点名本仓库处理专员 | 人工手动兜底 + 评审后自动闭环：评审 NPC 用 `@仓库路径(仓库处理专员)` 完整格式点名本仓库处理专员，触发其接手修复并**打标签**标记状态；本仓库 CodeBuddy 兜底。**禁止 push**。 |
| **驳回 → 必然触发打标签（放弃迭代 / 转交）** | 评审驳回但问题无法在本 PR 就地解决 | 修完必打标签（必然触发 `pull_request`）；没更新则打「适合关闭」/「适合推送」标签标记处置，或转其他 issue/PR 解决并关闭本 PR。**禁止 push**。 |
| **`failStages`（失败自动触发）** | stages 阶段（测试信号灯 / 评审 / 修复 / 合并门禁）任一失败 | **失败事件自动唤起本仓库处理专员**，全程无人工点名：可修代码 bug 就地修 + 补断言 + **打标签**（自然进入主闭环复审）；环境/权限类（如打标签权限不足）显式告警 @ 仓库负责人；无法就地解决则转交 / 打「适合关闭」标签标记。CodeBuddy 兜底。**禁止 push**。 |

> **一句话**：主闭环 `pull_request` 兜底所有修复打标签；`changes_requested` 兼容人工 git 级打回；
> `comment@npc` 兼容人类点名；驳回无法就地解决时以「放弃迭代 / 转交关闭」打标签对齐进度；
> **本系统故意设计不允许 push**（会触发 403 报错、破坏闭环）。
> **`failStages` 让失败事件自动把本仓库处理专员拉进流程**（红灯即自动处置，不靠人点名）。
> 四者并存，不替换；修复闭环优先本仓库处理专员，CodeBuddy 通用兜底。

## 🔗 召唤优先级链（逐个降级，一次只召唤一个）

修复闭环在需要召唤修复角色时，**必须遵循召唤优先级链**，而非一股脑同时召唤多个角色：

```
仓库处理专员  →  CodeBuddy  →  (兜底停止)
 (最高优先)      (只提供建议兜底)
```

- **一次只召唤一个**：先召唤链中当前最高优先级的角色；它能承接就停在那一级，
  解决不了（不可用 / 权限不足 / 超时）才**降级**召唤链中下一个角色，直到 CodeBuddy 兜底；
- **仓库处理专员是最高优先级**：它最懂本仓库的合并 / 修改 / 打标签标记状态，是本仓库修复闭环的第一执行者；
- **带壳完整格式即直接触发**：`@组织/仓库(仓库处理专员)` 或 `@组织/仓库(CodeBuddy)`
  就是直接召唤本仓库对应角色（非"禁止"，而是精确定位到对应仓库），无需额外动作；
- **召唤了对应仓库的带壳角色后，请勿再裸 `@CodeBuddy` / `@仓库处理专员`**：
  裸召唤可能路由到系统级或他仓 NPC，权限错位、内容对不上、无效空转；
- **代码实现**：`game-studio-agents/config/agent_identity.py` 的
  `get_review_operational_advice()`（默认优先仓库处理专员，支持 `role=` 指定）、
  `get_repair_priority_chain()`（返回优先级链）。

## 一、为什么需要这套护栏

评审（OCI / 代码审查员）在 PR 合并前拦截问题，这是有效的**质量护栏**。
但"评审打回 → 修复 → 再评审"如果无限循环，会：
- 消耗大量来回与资源；
- 让 AI 在某个长期无法解决的难点上空转；
- 掩盖真正需要人类决策的问题（改需求 / 改框架）。

所以：**默认直接改** + **最大 5 轮上限** + **超限反馈人类** + **多源触发按场景分**。

## 二、核心原则

| 原则 | 说明 |
|------|------|
| **默认直接改** | 评审返回的问题（尤其 bug）多数确实需要修，仓库处理专员收到打回后**直接修改并打标签标记**，不反复问"要不要改"。 |
| **先修 Bug，再修质量** | 按优先级：安全漏洞 / 潜在 Bug → 代码质量 → 性能 → 架构一致性。 |
| **修复固化为断言** | 每修一个评审点，往对应 `tests/*.sh` 加一条断言，**防止回退**，让 CI 持续守卫。 |
| **最大 5 轮护栏** | 同一 PR 的"评审→修复→再评审"来回最多 **5 次**。达到上限仍未解决 → 停止自动修复。 |
| **超限反馈人类** | 达上限后，仓库处理专员在 PR 评论中明确反馈人类，说明**需要改需求 / 改框架 / 调整评审标准**，不再盲修。 |

## 三、闭环流程（多源驱动）

### 3.1 主闭环：`pull_request`（方案 A，钩子没 bug 就停）

```
PR 提交 / 任何修复打标签 → 测试信号灯 → 自动分配评审人 → NPC/OCI 代码审查
    │
    ▼（仓库处理专员读最新评审结论）
    ├── 评审通过（无 bug）→ 合并门禁（approved）→ 自动合并【钩子停】
    ├── 需修改（未达 5 轮）→ @仓库处理专员就地修复 + 补断言 + 打标签
    │        └── 打标签触发新一轮 pull_request → 回到顶部（天然多轮循环）
    ├── 需修改（已达 5 轮）→ 反馈人类（改需求/框架），停止自动修复
    └── 无法就地解决（驳回但超范围）→ 转交其他 issue/PR 解决并关闭本 PR，
            或打「适合关闭」标签标记处置（禁止 push）
```

> **驳回必然触发打标签**：修完必打标签；没更新则打「适合关闭」/「适合推送」标签
> 标记处置——这样每次评审打回都伴随一次标签更新，必然触发 `pull_request` 主闭环，让评审/监控
> 能持续对齐并监控进度，而不是静默空转。

### 3.2 并行触发源

- **`pull_request.changes_requested`**：人类评审者以 git「需要改进」打回时触发，仓库处理专员默认直接修。
- **`pull_request.comment@npc`**：人类在 PR 评论中 @仓库处理专员 / @CodeBuddy 时触发，按指令处理（修复/探讨/落地机制）。

三者并存，按场景各司其职，不互相替换。

## 四、轮次计数与上限

- **谁来计数**：仓库处理专员按 **PR 内评审轮次** 记录（每次 `changes_requested → 修复 → 再评审` 计 1 轮）。
- **上限**：`MAX_FIX_ROUNDS = 10`。
- **到达上限的判断**：第 5 轮修复后若评审仍返回 `changes_requested` / `需修改`，
  仓库处理专员 **不再发起第 11 轮修复**，改为：
  1. 在 PR 评论中总结「已修复的点」与「仍无法解决的点及根因」；
  2. 明确 @ 人类（仓库负责人）介入；
  3. 建议下一步：改需求（拆小范围）/ 改框架（重构该模块）/ 调整评审标准（降低误报）。
- **何时重置计数**：当 PR 的评审结论从"需修改"变为"通过/已批准"后，后续若因新需求再次打回，是新一轮评审，重新计数。

## 五、上下文路由机制（全局ID + sessionID，降级显性化）

> 回应机制改进方向：「**评审后再修 bug 应该让提交该 PR 的对话自己改**，这样上下文正好
> 用上，问题可能更好解决」——为此需要**路由机制 + 全局ID + sessionID** 生效。

### 5.1 为什么要上下文路由

评审打回后，修复质量高度依赖**能否延续原对话的上下文**：提交 PR 时已经带着需求背景、
架构约束、改动意图，若修复时把这些上下文丢掉，等于让仓库处理专员重新理解一个陌生 PR，
修复效果会显著变弱。**让提交 PR 的对话自己改**，正是用上已沉淀的上下文。

### 5.2 路由机制（上下文路由，默认优先）

实现见 `game-studio-agents/config/review_fix_router.py`（`ReviewFixRouter`，与具体岗位/部门完全解耦）：

1. **提交时注册**：提交 PR / 工作包时，用 `register_context(global_id, session_id, payload)`
   注册原对话上下文。其中 `global_id` 是**全局ID**（PR/工作包唯一标识），`session_id` 是
   **sessionID**（原对话会话标识）。
2. **评审打回时路由**：`route_review(global_id, review)` 按 `global_id` 定位到原对话上下文
   （`session_id`），继承**完整上下文 + 历次评审-修复历史（history）** 来修复 → 走
   `session_route`（上下文路由），信息细节不丢失，修复效果最强。
3. **修复沉淀**：`record_fix(global_id, fix)` 把每次修复追加到上下文历史，供后续轮次复用。

### 5.3 降级显性化（哈希校验兜底，禁止静默降级）

当上下文路由**不可用**（如原对话已失效 / 从未注册 `session_id`）时，降级到**哈希校验**
兜底（基于 `global_id` + 评审内容做确定性匹配）。**但这个降级必须有显性说明**，
禁止静默降级：

- **降级必须输出 `route_fallback` 显性告警**：说明降级原因 + 本次丢失的上下文信息
  （对话历史、提交上下文、历史评审-修复记录）；
- **为什么不能静默降级**：一旦静默降级，崩溃后不会被人察觉修复，会一直用哈希——
  哈希匹配**不带任何上下文细节**，修复效果持续变弱，且无从追责与恢复；
- **降级可观测**：`ReviewFixRouter.summary()` 统计 `context_registered` / `session_ids` /
  `hash_fallback_count` / `degraded`，可随时核查有多少 PR 在降级哈希中；
- **恢复路径**：只要后续对同一 `global_id` 重新 `register_context`，即恢复上下文路由，
  不再依赖哈希。

> **一句话**：默认走上下文路由（全局ID + sessionID 用上原对话上下文）；路由不可用时
> 降级到哈希校验兜底，但**降级必须显性说明**（原因 + 丢失信息），绝不静默——
> 否则崩了不修，会一直用哈希、丢失上下文细节、效果持续变弱。

## 六、落地位置

| 位置 | 作用 |
|------|------|
| `.cnb.yml` → `pull_request` | **主闭环触发源**：`测试信号灯 → 评审 → 仓库处理专员闭环修复（就地改+补断言+打标签）→ 合并门禁`。钩子没 bug 就停；驳回必然触发打标签。**禁止 push**。 |

| `.cnb.yml` → `pull_request` → **`failStages`** | **失败自动触发**：stages 失败时自动唤起仓库处理专员处置（可修就修+补断言+打标签；权限/环境类显式告警；无法就地解决则转交/打「适合关闭」标签）。**禁止 push**。 |
| `game-studio-agents/config/review_fix_router.py` | **上下文路由机制**：全局ID + sessionID 定位原对话，降级到哈希校验时显性告警。 |
| `tests/test_review_fix_loop.sh` | 上下文路由 + 降级显性化断言，未通过即红灯阻塞。 |
| `.cnb/settings.yml` | 定义 `仓库处理专员` 与 `CodeBuddy` 角色（供 `npc:go` 解析），与 `.cnb.yml` 全部 role 引用对齐。修复闭环优先仓库处理专员，CodeBuddy 通用兜底。 |
| `tests/*.sh` | 测试信号灯护栏，把修复点固化为断言，未通过即红灯阻塞。 |
| 本文档 | 运行规范，供仓库处理专员（优先）/ CodeBuddy（兜底）执行与团队交接。 |

## 七、怎么确保它稳定生效

1. **把护栏写进流水线（主触发源 pull_request）**：`.cnb.yml` 的 `pull_request` 流水线内含
   `评审 → 闭环修复 → 打标签`，任何修复打标签都会重跑整条链，评审打回必然触发打标签（修完必打标签），
   不依赖某个单一事件是否被平台触发。
2. **多源并存防遗漏**：`pull_request`（主闭环）+ `changes_requested`（人工 git 打回）+
   `comment@npc`（人类点名）并存，即使某个触发源断掉，另两个仍能兜住。
3. **修复点固化成断言**：每修一个评审点就加断言，谁再改回 bug，CI 立刻红灯，不悄悄回退。
4. **轮次上限显式化**：`MAX_FIX_ROUNDS=10` 作为执行规范常量，仓库处理专员每次评审打回都核对轮次，杜绝无限循环。
5. **上下文路由优先 + 降级显性化**：评审打回优先路由到原对话上下文（全局ID + sessionID），
   上下文不可路由降级到哈希校验时**必须输出 `route_fallback` 显性告警**，禁止静默降级。
6. **标签驱动强制自检（防静默卡死，正确身份调取）**：仓库处理专员每次修复后必须**打标签**标记状态，并立即验证是否成功——
   - 若打标签成功，确认触发新一轮 `pull_request` 评审后继续闭环；
   - 若打标签因权限返回错误：**立即停止打标签，绝不再重复尝试**。**不是补权限的问题，
     是调用身份错了**——权限错误说明本次执行所用
     身份不是**本仓库绑定的仓库处理专员**（对应仓库下具备合并/关闭 Issue 权限的那个），而是
     评审 NPC 或其他仓库的 CodeBuddy（其职责只是读和审，本就不具备操作权限）。这是调取错误被
     护栏拦住了，属于护栏正常生效，**不做补权限处理**。重试只会反复报错空转，
     **只做一次显式告警**即结束本阶段，绝不反复尝试打标签。
   - **正确身份调取（防跨仓库/错身份卡死）**：告警的同时**带上完整说明文本 + 召唤壳**。
     **先运行** `python3 game-studio-agents/config/agent_identity.py`（AgentIdentity 模块）从环境变量
     `CNB_REPO_SLUG` 探测当前仓库 slug（不写死仓库名），然后用探测到的完整格式
     `@<探测到的slug>(仓库处理专员)`（仓库路径 + 角色名）
     定位到**本仓库的仓库处理专员**，触发 `pull_request.comment@npc` 让本仓库仓库处理专员接手
     完成本次打标签——说明文本写明已修复点、本次打标签因执行身份不是本仓库仓库处理专员
     被拒绝、请本仓库仓库处理专员用其自带权限打标签并核对触发新一轮评审。
     **不能用裸 @**（裸 @ 会命中系统级或他仓 NPC，权限不对）；若本仓库未部署仓库处理专员，
     可降级召唤本仓库 CodeBuddy 兜底（同样用完整格式）；
   - 主闭环在合并门禁前新增**「评审闭环健康检查」阶段**，检测"修复打了标签但评审没跟上"的
     假完成状态，发现闭环中断（打标签 / 评审触发 / 评审结论缺失）即显式告警并中断放行。
   - **「正常待评审」 vs 「真正闭环中断」判别规则**（健康检查不误报的关键）：
     - **正常待评审**（应放行，不中断）：本 run 内仓库处理专员修复并打标签后，修复会触发**下一轮**
       pull_request 评审 run，此刻本 run 拿不到最新 head 的评审结论是**正常状态**——只要打标签成功
       且已触发新一轮评审事件，即视为闭环正常推进，放行等下一轮跟进，**不得**仅因"最新 head 暂无
       评审结论"就判中断；
     - **真正闭环中断**（须满足至少一个硬性信号，否则不算中断）：① 打标签失败（身份非本仓库
       仓库处理专员 / 执行 agent 权限不足）且修复状态未正确标记；② 打标签成功但长时间无后续评审 run
       跟进；③ 评审结论长期停留"需修改"且超 5 轮上限未收敛。满足任一信号才显式告警并中断放行。
   > 这条护栏回应了实际踩过的坑：评审→修复→打标签闭环曾在"打标签"这一步因调用身份不对（非本仓库
   > 修复专员）被拦截，表现为"修复完成但一直没触发下一轮评审"，看似评审机制失效，实为
   > 打标签未成功且无告警。**正确处置是调取本仓库处理专员（仓库路径+角色名完整定位），不是补权限**。
   > **同时避免误伤**：修复后打标签成功、新评审尚在下一轮才产生时，绝不能因"暂无最新评审结论"
   > 就误报"闭环中断"，否则每次合法修复都会被拦下、评审闭环反而无法收敛。

## 八、不能稳定运作时怎么恢复和升级

### 恢复（出问题先止损）
- **打标签失败 / 调用身份错误**：若评审修复后打标签返回错误，**立即停止打标签，绝不再重复尝试**
  （重试只会反复报错空转）。**不是补权限的问题，是调用身份错了**。
  权限错误说明本次执行所用身份不是**本仓库绑定的仓库处理专员**（对应仓库下具备合并/关闭 Issue
  权限的那个），而是评审 NPC 或其他仓库的 CodeBuddy（其职责只是读和审，本就不具备操作权限）。
  这是调取错误被护栏拦住，属于护栏正常生效。只做一次显式告警即结束，绝不重复尝试。处置方式：
  1. **正确身份调取（推荐，无需人工介入）**：在本 PR 评论中带上完整说明文本 + 召唤壳，
     用「`@<通过 agent_identity.py 探测的当前仓库slug>(仓库处理专员)`」完整格式（仓库路径 + 角色名）
     定位到**本仓库的仓库处理专员**，触发 `pull_request.comment@npc` 让本仓库仓库处理专员接手
     完成本次打标签——本仓库仓库处理专员自带对应权限，可绕过错误身份的限制。**不能用裸 @**
     （裸 @ 会命中系统级或他仓 NPC，权限不对）；
     若本仓库未部署仓库处理专员，可降级召唤本仓库 CodeBuddy 兜底（同样用完整格式）；
  2. **不补权限**：本仓库仓库处理专员 / CodeBuddy 已具备合并/关闭 Issue 权限，无需给
     任何 token 补充额外权限。
  **修复完打标签不上必须显式告警 + 用正确身份调取，禁止静默结束。**
- **看 CI 红灯**：进入 `.cnb.yml` 测试信号灯构建日志（`cnb pulls get-ci-logs`），定位哪条断言失败——这是"哪里被破坏"的最快定位。
- **回滚策略**：声明化配置（如 `progress_pusher_policy.yaml`）改配置不碰代码，若调崩了 `git revert` 该文件即可。
- **回滚代码**：`git checkout <上一提交> -- <文件>` 恢复，再跑测试信号灯确认转绿。
- **超限止损**：达到 5 轮上限时停止自动修复，由人类介入改需求/框架，避免仓库处理专员继续空转。
- **降级排查**：若发现某 PR 一直在用哈希校验（`summary()` 的 `degraded` 非空），说明其上下文路由
  失效——检查是否未 `register_context` 或 `session_id` 失效，补齐注册即可恢复上下文路由，
  避免持续丢上下文。

### 升级（持续增强这个机制）
- **加测试 = 加护栏**：每修一个 bug 就加断言，断言越多机制越牢。
- **提升评审深度**：OCI 的 `critical/warning/info` 分级 + 合并门禁已能拦严重问题；想更严可在 `.cnb.yml` 的 `pull_request` 阶段加评审人数量/指定资深评审人。
- **调整护栏参数**：若某 PR 结构复杂、5 轮仍合理，可临时提高上限（如 15）；但**不建议默认放宽**，超限往往意味着需要人类改需求/框架，而非继续多修几轮。
- **上下文路由增强**：把提交时的 `register_context` 与平台对话/PR 环境变量（`CNB_PULL_REQUEST_*`、
  `CNB_REVIEW_ID` 等）打通，让提交 PR 的对话在评审打回时天然命中原上下文。

## 九、一句话总结

**评审返回 bug → 默认直接改**（把质量护栏前置到合并前）+ **最大 5 轮防循环** +
**超限反馈人类改需求/框架**；它"稳定生效"靠**护栏进 CI + 修复点固化成断言 + 轮次显式计数**。
同时**评审打回优先路由到原对话上下文（全局ID + sessionID）**，上下文不可用降级到哈希校验时
**必须显性告警、绝不静默**，避免一直丢上下文导致修复效果持续变弱。
