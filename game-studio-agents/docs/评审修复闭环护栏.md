# 评审-修复闭环护栏（Review-Fix Loop Guardrail）

> 运行规范，确保「CL/OCI 评审返回问题 → CodeBuddy 自动修复」这个闭环
> **稳定生效、有上限、不陷入无限循环**，并**多源触发、按场景分**。回应团队提出的机制改进方向。

## 〇、多源触发，按场景分（回应：触发信号不应只支持一种）

> 触发信号不是只能支持一种的——**允许不同源的触发方式而不是互相替换，都兼容才是对的**。
> 每种触发源覆盖不同场景，并存互补，各取所长：

| 触发源（.cnb.yml 事件） | 适用场景 | 作用 |
|------------------------|---------|------|
| **`pull_request`（主闭环 / 方案 A）** | CodeBuddy 修复后自动重跑（修完必打标签） | 最核心触发源：`测试信号灯 → 评审 → CodeBuddy 就地修复并**打标签**标记状态（如「适合推送」）→ 触发新一轮 pull_request`，形成天然多轮循环；**钩子没 bug 就停**（评审通过即不再改）。**本系统故意设计不允许 push**：评审闭环通过打标签驱动，任何 NPC 不得尝试 push（会触发 403 报错、破坏闭环）。 |
| **`pull_request.changes_requested`** | 人工评审者以 git「需要改进」形式打回 | 兼容人工 git 级打回，与主闭环并存。 |
| **`pull_request.comment@npc`** | 人类主动 @CodeBuddy；评审 NPC 评审后点名本仓库 CodeBuddy | 人工手动兜底 + 评审后自动闭环：评审 NPC 用 `@仓库路径(CodeBuddy)` 完整格式点名本仓库 CodeBuddy，触发其接手修复与**打标签**标记状态（而非 push）。 |
| **驳回 → 打标签标记状态（放弃迭代 / 转交）** | 评审驳回但问题无法在本 PR 就地解决 | 修完必打标签（必然触发 `pull_request`）；没更新则**打「适合关闭」标签**标记放弃此部分迭代，或转其他 issue/PR 解决并关闭本 PR。**禁止 push**（本系统故意设计不允许 push）。 |
| **`failStages`（失败自动触发）** | stages 阶段（测试信号灯 / 评审 / 修复 / 合并门禁）任一失败 | **失败事件自动唤起 CodeBuddy**，全程无人工点名：可修代码 bug 就地修 + 补断言 + **打「适合推送」标签**（触发复审）；权限类（如打标签权限不足）显式告警 @ 仓库负责人；无法就地解决则转交 / 打「适合关闭」标签标记。**禁止 push**（本系统故意设计不允许 push）。 |

> **一句话**：主闭环 `pull_request` 兜底所有修复打标签；`changes_requested` 兼容人工 git 级打回；
> `comment@npc` 兼容人类点名；驳回无法就地解决时以「放弃迭代 / 转交关闭」**打标签**标记状态；
> **`failStages` 让失败事件自动把 CodeBuddy 拉进流程**（红灯即自动处置，不靠人点名）。
> 四者并存，不替换。**本系统故意设计不允许 push**：评审闭环通过打标签驱动，
> 任何 NPC 不得尝试 push（会触发 403 报错、破坏闭环），也不得输出"push 失败 / 403"类错误信息。

## 一、为什么需要这套护栏

评审（OCI / 代码审查员）在 PR 合并前拦截问题，这是有效的**质量护栏**。
但"评审打回 → 修复 → 再评审"如果无限循环，会：
- 消耗大量来回与资源；
- 让 AI 在某个长期无法解决的难点上空转；
- 掩盖真正需要人类决策的问题（改需求 / 改框架）。

所以：**默认直接改** + **最大 10 轮上限** + **超限反馈人类** + **多源触发按场景分**。

## 二、核心原则

| 原则 | 说明 |
|------|------|
| **默认直接改** | 评审返回的问题（尤其 bug）多数确实需要修，CodeBuddy 收到打回后**直接修改并重新提交**，不反复问"要不要改"。 |
| **先修 Bug，再修质量** | 按优先级：安全漏洞 / 潜在 Bug → 代码质量 → 性能 → 架构一致性。 |
| **修复固化为断言** | 每修一个评审点，往对应 `tests/*.sh` 加一条断言，**防止回退**，让 CI 持续守卫。 |
| **最大 10 轮护栏** | 同一 PR 的"评审→修复→再评审"来回最多 **10 次**。达到上限仍未解决 → 停止自动修复。 |
| **超限反馈人类** | 达上限后，CodeBuddy 在 PR 评论中明确反馈人类，说明**需要改需求 / 改框架 / 调整评审标准**，不再盲修。 |

## 三、闭环流程（多源驱动）

### 3.1 主闭环：`pull_request`（方案 A，钩子没 bug 就停）

```
PR 提交 / 任何修复打标签 → 测试信号灯 → 自动分配评审人 → NPC/OCI 代码审查
    │
    ▼（CodeBuddy 读最新评审结论）
    ├── 评审通过（无 bug）→ 合并门禁（approved）→ 自动合并【钩子停】
    ├── 需修改（未达 10 轮）→ CodeBuddy 就地修复 + 补断言 + 打「适合推送」标签
    │        └── 打标签触发新一轮 pull_request → 回到顶部（天然多轮循环）
    ├── 需修改（已达 10 轮）→ 反馈人类（改需求/框架），停止自动修复
    └── 无法就地解决（驳回但超范围）→ 转交其他 issue/PR 解决并关闭本 PR，
            或**打「适合关闭」标签**标记「放弃此部分迭代」
```

> **驳回必然打标签**：修完必打「适合推送」标签；没更新则打「适合关闭」标签标记
> 放弃此部分迭代——这样每次评审打回都伴随一次标签操作，必然触发 `pull_request`
> 主闭环，让评审/监控能持续对齐并监控进度，而不是静默空转。
> **本系统故意设计不允许 push**：任何 NPC 不得尝试 push（会触发 403 报错、破坏闭环）。

### 3.2 并行触发源

- **`pull_request.changes_requested`**：人类评审者以 git「需要改进」打回时触发，CodeBuddy 默认直接修。
- **`pull_request.comment@npc`**：人类在 PR 评论中 @CodeBuddy 时触发，按指令处理（修复/探讨/落地机制）。

三者并存，按场景各司其职，不互相替换。

## 四、轮次计数与上限

- **谁来计数**：CodeBuddy 按 **PR 内评审轮次** 记录（每次 `changes_requested → 修复 → 再评审` 计 1 轮）。
- **上限**：`MAX_FIX_ROUNDS = 10`。
- **到达上限的判断**：第 10 轮修复后若评审仍返回 `changes_requested` / `需修改`，
  CodeBuddy **不再发起第 11 轮修复**，改为：
  1. 在 PR 评论中总结「已修复的点」与「仍无法解决的点及根因」；
  2. 明确 @ 人类（仓库负责人）介入；
  3. 建议下一步：改需求（拆小范围）/ 改框架（重构该模块）/ 调整评审标准（降低误报）。
- **何时重置计数**：当 PR 的评审结论从"需修改"变为"通过/已批准"后，后续若因新需求再次打回，是新一轮评审，重新计数。

## 五、上下文路由机制（全局ID + sessionID，降级显性化）

> 回应机制改进方向：「**评审后再修 bug 应该让提交该 PR 的对话自己改**，这样上下文正好
> 用上，问题可能更好解决」——为此需要**路由机制 + 全局ID + sessionID** 生效。

### 5.1 为什么要上下文路由

评审打回后，修复质量高度依赖**能否延续原对话的上下文**：提交 PR 时已经带着需求背景、
架构约束、改动意图，若修复时把这些上下文丢掉，等于让 CodeBuddy 重新理解一个陌生 PR，
修复效果会显著变弱。**让提交 PR 的对话自己改**，正是用上已沉淀的上下文。

### 5.2 路由机制（上下文路由，默认优先）

实现见 `config/review_fix_router.py`（`ReviewFixRouter`，与具体岗位/部门完全解耦）：

1. **提交时注册**：提交 PR / 工作包时，用 `register_context(global_id, session_id, payload)`
   注册原对话上下文。其中 `global_id` 是**全局ID**（PR/工作包唯一标识），`session_id` 是
   **sessionID**（原对话会话标识）。
2. **评审打回时路由**：`route_review(global_id, review)` 按 `global_id` 定位到原对话上下文
   （`session_id`），继承**完整上下文 + 历次评审-修复历史（history）** 来修复 → 走
   `session_route`（上下文路由），信息细节不丢失，修复效果最强。
3. **修复沉淀**：`record_fix(global_id, fix)` 把每次修复追加到上下文历史，供后续轮次复用。

### 5.3 降级显性化（哈希校验兜底，禁止静默降级）

当上下文路由**不可用**（如原对话已失效 / 从未注册 `session_id`）时，降级到**哈希校验**
兜底（基于 `global_id` + 评审内容做确定性匹配）。**但这个降级必须有显性说明**，
禁止静默降级：

- **降级必须输出 `route_fallback` 显性告警**：说明降级原因 + 本次丢失的上下文信息
  （对话历史、提交上下文、历史评审-修复记录）；
- **为什么不能静默降级**：一旦静默降级，崩溃后不会被人察觉修复，会一直用哈希——
  哈希匹配**不带任何上下文细节**，修复效果持续变弱，且无从追责与恢复；
- **降级可观测**：`ReviewFixRouter.summary()` 统计 `context_registered` / `session_ids` /
  `hash_fallback_count` / `degraded`，可随时核查有多少 PR 在降级哈希中；
- **恢复路径**：只要后续对同一 `global_id` 重新 `register_context`，即恢复上下文路由，
  不再依赖哈希。

> **一句话**：默认走上下文路由（全局ID + sessionID 用上原对话上下文）；路由不可用时
> 降级到哈希校验兜底，但**降级必须显性说明**（原因 + 丢失信息），绝不静默——
> 否则崩了不修，会一直用哈希、丢失上下文细节、效果持续变弱。

## 七、怎么确保它稳定生效

1. **把护栏写进流水线（主触发源 pull_request）**：`.cnb.yml` 的 `pull_request` 流水线内含
   `评审 → 闭环修复 → 打标签`，任何修复打标签都会重跑整条链，评审打回必然**打「适合推送」标签**
   标记状态（修完必打标签），不依赖某个单一事件是否被平台触发。
   **本系统故意设计不允许 push**：任何 NPC 不得尝试 push（会触发 403 报错、破坏闭环）。
2. **多源并存防遗漏**：`pull_request`（主闭环）+ `changes_requested`（人工 git 打回）+
   `comment@npc`（人类点名）并存，即使某个触发源断掉，另两个仍能兜住。
3. **修复点固化成断言**：每修一个评审点就加断言，谁再改回 bug，CI 立刻红灯，不悄悄回退。
4. **轮次上限显式化**：`MAX_FIX_ROUNDS=10` 作为执行规范常量，CodeBuddy 每次评审打回都核对轮次，杜绝无限循环。
5. **上下文路由优先 + 降级显性化**：评审打回优先路由到原对话上下文（全局ID + sessionID），
   上下文不可路由降级到哈希校验时**必须输出 `route_fallback` 显性告警**，禁止静默降级。
6. **标签驱动强制自检（防静默卡死）**：CodeBuddy 每次修复后必须**打标签**标记状态
   （如「适合推送」/「适合合并」），并立即验证标签是否成功——
   - 若标签成功，确认触发新一轮 `pull_request` 评审后继续闭环；
   - 若打标签失败 / 权限不足：在 PR 评论中显式告警说明失败原因与已完成的修复点，
     请求人工或正确身份处理；
   - **禁止尝试 push**：本系统故意设计不允许 push（会触发 403 报错、破坏闭环）。
     任何 NPC 不得尝试 push，也不得在评论中输出"push 失败 / 403"类错误信息。
     这是护栏正常生效，不是权限问题，**不做补权限处理**。
   - 主闭环在合并门禁前新增**「评审闭环健康检查」阶段**，检测"修复打了标签但评审没跟上"的
     假完成状态，发现闭环中断（标签 / 评审触发 / 评审结论缺失）即显式告警并中断放行。
   - **「正常待评审」 vs 「真正闭环中断」判别规则**（健康检查不误报的关键）：
     - **正常待评审**（应放行，不中断）：本 run 内 CodeBuddy 修复并打「适合推送」标签后，
       打标签会触发**下一轮** pull_request 评审 run，此刻本 run 拿不到最新 head 的评审结论是
       **正常状态**——只要标签已打且已触发新一轮评审事件，即视为闭环正常推进，放行等下一轮
       跟进，**不得**仅因"最新 head 暂无评审结论"就判中断；
     - **真正闭环中断**（须满足至少一个硬性信号，否则不算中断）：① 打标签失败（修复状态
       未正确标记）；② 标签已打但长时间无后续评审 run 跟进；③ 评审结论长期停留"需修改"且
       超 10 轮上限未收敛。满足任一信号才显式告警并中断放行。
     - **注意**：**禁止将"push 403"作为中断信号**——本系统故意设计不允许 push，任何 NPC
       都不应尝试 push，也就不会产生 push 403 错误。
   > **本系统故意设计不允许 push**：评审闭环通过打标签驱动（如「适合合并」「适合关闭」
   > 「适合推送」），不依赖 push 事件。任何 NPC 不得尝试 push（会触发 403 报错、破坏闭环），
   > 也不得输出"push 失败 / 403"类错误信息。

## 八、不能稳定运作时怎么恢复和升级

### 恢复（出问题先止损）
- **本系统故意设计不允许 push**：评审闭环通过**打标签**驱动（如「适合合并」「适合关闭」
  「适合推送」），不依赖 push 事件。任何 NPC **不得尝试 push**（会触发 403 报错、破坏闭环），
  也不得在评论中输出"push 失败 / 403"类错误信息。
- **打标签失败**：若修复后打标签（如「适合推送」）失败 / 权限不足：在 PR 评论中显式告警
  说明失败原因与已完成的修复点，请求人工或正确身份处理。**不补权限**。
- **看 CI 红灯**：进入 `.cnb.yml` 测试信号灯构建日志（`cnb pulls get-ci-logs`），定位哪条断言失败——这是"哪里被破坏"的最快定位。
- **看 CI 红灯**：进入 `.cnb.yml` 测试信号灯构建日志（`cnb pulls get-ci-logs`），定位哪条断言失败——这是"哪里被破坏"的最快定位。
- **回滚策略**：声明化配置（如 `progress_pusher_policy.yaml`）改配置不碰代码，若调崩了 `git revert` 该文件即可。
- **回滚代码**：`git checkout <上一提交> -- <文件>` 恢复，再跑测试信号灯确认转绿。
- **超限止损**：达到 10 轮上限时停止自动修复，由人类介入改需求/框架，避免 CodeBuddy 继续空转。
- **降级排查**：若发现某 PR 一直在用哈希校验（`summary()` 的 `degraded` 非空），说明其上下文路由
  失效——检查是否未 `register_context` 或 `session_id` 失效，补齐注册即可恢复上下文路由，
  避免持续丢上下文。

### 升级（持续增强这个机制）
- **加测试 = 加护栏**：每修一个 bug 就加断言，断言越多机制越牢。
- **提升评审深度**：OCI 的 `critical/warning/info` 分级 + 合并门禁已能拦严重问题；想更严可在 `.cnb.yml` 的 `pull_request` 阶段加评审人数量/指定资深评审人。
- **调整护栏参数**：若某 PR 结构复杂、10 轮仍合理，可临时提高上限（如 15）；但**不建议默认放宽**，超限往往意味着需要人类改需求/框架，而非继续多修几轮。
- **上下文路由增强**：把提交时的 `register_context` 与平台对话/PR 环境变量（`CNB_PULL_REQUEST_*`、
  `CNB_REVIEW_ID` 等）打通，让提交 PR 的对话在评审打回时天然命中原上下文。

## 九、一句话总结

**评审返回 bug → 默认直接改**（把质量护栏前置到合并前）+ **最大 10 轮防循环** +
**超限反馈人类改需求/框架**；它"稳定生效"靠**护栏进 CI + 修复点固化成断言 + 轮次显式计数**。
同时**评审打回优先路由到原对话上下文（全局ID + sessionID）**，上下文不可用降级到哈希校验时
**必须显性告警、绝不静默**，避免一直丢上下文导致修复效果持续变弱。
