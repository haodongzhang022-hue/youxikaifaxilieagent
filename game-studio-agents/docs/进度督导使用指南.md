# 进度督导（Progress Pusher）使用指南

> 稳定可用的部署与用法说明。回答"**进度督导是 skill / 声明 / 程序规则 哪种更合适**"。

## 一、结论：三者分层，缺一不可

进度督导不是"三选一"，而是 **三层各司其职**，组合起来才"稳定可生效"：

| 层 | 承载 | 解决的问题 | 为什么缺了不行 |
|----|------|-----------|---------------|
| **程序规则化**（核心） | `config/progress_pusher.py` | 让督导**真正生效**：接入总线、定时扫描、确定性决策、发出催办/升级 | 只声明不执行 → 督导永远"没生效" |
| **声明（策略）** | `config/progress_pusher_policy.yaml` | 阈值/节奏/打扰成本可调，**不碰代码**即稳定复现 | 全部硬编码 → 改行为要动代码，易错 |
| **skill / 用法** | 本文档 | 说明怎么部署、怎么调、怎么验证（**用法稳定可用**） | 没有用法 → 别人不知道怎么落地 |

> 一句话：**程序规则负责"生效"，声明负责"可调"，skill 负责"会用"**。
> 这与项目里 `message_bus/task_scheduler`（机制）+ `agent_boost/*.yaml`（可插拔预设）+ README（用法）的分层是一致的。

## 二、文件清单

| 文件 | 作用 |
|------|------|
| `config/progress_pusher.py` | 进度督导 Agent（继承 BaseAgent，规则引擎，接入总线） |
| `config/progress_pusher_policy.yaml` | **声明化策略**（阈值/节奏/打扰成本/升级规则） |
| `config/task_scheduler.py` / `message_bus.py` / `agent_core.py` | 复用的底层基础设施（v0.3，main 已有） |

| `tests/test_progress_pusher.sh` | 测试信号灯（CI 护栏） |

## 四、接入到真实调度（程序规则化如何"生效"）

```python
from message_bus import MessageBus
from task_scheduler import Scheduler, TaskQueue
from progress_pusher import ProgressPusherAgent, attach_to_scheduler

bus = MessageBus()
queue = TaskQueue()
sched = Scheduler(queue=queue, bus=bus)

# 创建进度督导并挂到同一任务队列
pusher = ProgressPusherAgent(bus=bus, queue=queue)
attach_to_scheduler(sched, pusher)   # 与调度器共享同一份任务
pusher.boot()

# 任务由 scheduler 派发执行，进度督导负责盯 DDL 催办/升级
# 督导心跳会定时扫描 TaskQueue；也可手动触发：
pusher.scan()
bus.process_all()   # 让催办/升级消息真正经总线派发
```

**生效链路**：`TaskQueue`（任务状态）→ 督导 `heartbeat/scan` 扫描 → `DecisionEngine` 规则决策（WATCH/PUSH/WARN/ESCALATE）→ `MessageBus` 发出 `NOTIFICATION` 给 owner / 项目经理。

> **必须共享总线**：`ProgressPusherAgent` 一定要传入与调度器一致的 `bus`，并在发送后调用
> `bus.process_all()`，否则消息只入队不投递（`delivered=0`），“真正生效”会落空。
> `collaboration_support.ProgressPusher` 薄封装已自动传入共享总线并暴露 `drain()`。
>
> **状态机**：督导采用生态状态 `IDLE/TRACKING/PUSHING/ESCALATING/WARNING`（与 `ecosystem_roles.yaml`
> / `roles.yaml` 声明一致），覆写了基类通用生命周期，故 `_do_push/_do_escalate` 的
> `PUSHING/ESCALATING` 转换合法、不触发 `state_fail`。

## 五、策略调优（声明化，改 YAML 即可）

`config/progress_pusher_policy.yaml` 里可调的关键参数：

| 参数 | 默认 | 说明 |
|------|------|------|
| `lag_threshold_days` | 2.0 | 逾期 ≥ 该天数且未完成 → 判定落后并催办（PUSH） |
| `near_ddl_warn_hours` | 12.0 | 距 DDL 不足该小时 → 友好预警（WARN） |
| `block_timeout_hours` | 24.0 | 阻塞超该小时 → 升级项目经理（ESCALATE） |
| `push_cooldown_hours` | 6.0 | 同任务两次催办最小间隔（**打扰成本控制**） |
| `max_pushes_per_task` | 3 | 单任务最多催办次数，超出必须升级，不无效催办 |
| `scan_interval_sec` | 30.0 | 心跳扫描间隔；`<=0` 则仅事件驱动 |
| `escalate_to` | project_manager | 升级上报对象 |
| `reminder_intensity` | - | 催办力度分级措辞（watch/warn/push/escalate） |

**稳定原则**：改策略不碰代码 → 行为可复现、可回滚、可测试。

## 六、决策规则（程序规则化 · 确定性）

规则按顺序匹配，命中即返回：

1. **ESCALATE**：`state=BLOCKED` 且阻塞时长 ≥ `block_timeout_hours` → 升级项目经理
2. **ESCALATE**：单任务累计催办已达 `max_pushes_per_task` 且仍未完成 → 升级项目经理（**不再无效催办**，与策略声明一致）
3. **PUSH**：逾期 ≥ `lag_threshold_days` 且未完成、未冷却、催办次数未超上限 → 催办 owner
4. **WARN**：临近 DDL（< `near_ddl_warn_hours`）且未完成、未冷却 → 友好提醒
5. **WATCH**（兜底）：其余一律只跟踪，不打扰

**打扰成本控制**：冷却期 + 最大催办次数，避免"过度打扰"导致反效果；催满次数后强制升级，杜绝无限无效催办。

**事件驱动**：订阅 `task_events` 主题，任务状态变化（完成/阻塞/失败）会**即时触发对该任务的重新督导**，无需等下一次心跳扫描。

## 八、常见问题

- **督导没生效？** 检查是否调用了 `attach_to_scheduler` 与 `bus.process_all()`；策略 `enabled: false` 会进入观察态不催办。
- **催得太频繁？** 调大 `push_cooldown_hours` 或调小 `max_pushes_per_task`。
- **想只观察不打扰？** 把 `reminder_intensity` 全设 `watch`，或 `enabled: false`。
- **与 producer 是否双督导重复？** 不重复。producer 的 `heartbeat` 只负责**阻塞/依赖级联**提示（打回解锁下游等结构问题）；本角色专责**逾期/催办/升级**的时间进度督导，两者职责互补。该角色已登记进 `config/roles.yaml`，属协作支持圈。
- **producer 不再盯逾期后谁管？** 用 `run_end_to_end.py` 的一键挂载（`with_progress_pusher=True`）或 `attach_progress_pusher()` 把进度督导挂到共享链路，避免“逾期无人盯守”。
- **部门无法识别？** 该角色属**生态角色**（非六大执行部门），已在 `DEPT_KEY_BY_NAME` 中登记 `协作支持圈→support`，`preset_instantiator.validate()` 可识别，不再报“无法识别的部门”。
