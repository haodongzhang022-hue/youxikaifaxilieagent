# 框架自升级闭环（FRAMEWORK UPGRADE）

> 定义**何时升级框架、如何评估升级、由谁拍板、如何留痕**的完整闭环。
> 解决"框架演进没有沉淀方式"的 P0 缺口，让框架版本平滑演进、每次升级可追溯。

---

## 〇、为什么需要框架自升级闭环

框架（本仓库的 Agent 协作机制、流水线、文档体系）在持续演进，但**何时升级、怎么升级、
谁拍板、如何留痕**缺少明确的判定标准与流程。导致：

- 新能力调研发现 P0 缺口时，无明确触发路径推进升级；
- 评审反复指出同类问题时，无系统性沉淀通道；
- 框架版本演进线不清晰，无法平滑从当前版本升级到下一版。

**本闭环提供**：触发条件 → 评估流程 → 决策机制 → 落地留痕，四个环节环环相扣。

---

## 一、触发条件（何时需要升级框架）

> 以下任一条件满足，即触发框架升级评估。**不满足不升级**，避免框架频繁变动。

| 触发信号 | 判定标准 | 示例 |
|---------|---------|------|
| **新能力调研发现 P0 缺口** | 新能力调研 / 技术选型中发现现有框架存在 P0 级架构缺口 | 调研发现共享记忆缺少版本管理，需框架级支持 |
| **评审反复指出同类问题** | 同一 PR / 多次评审中，同一类问题被指出 **≥3 次** | 多次评审反馈"代码风格不一致"，需框架级统一规范 |
| **用户提出新架构诉求** | 用户（人类）明确提出新架构能力要求 | 用户要求支持多租户 / 多部门独立协作 |
| **10 轮修复上限触发** | 同一 PR 的"评审→修复"达 10 轮仍未收敛 | 修复反复不过，根因指向框架设计缺陷而非代码 bug |
| **多源触发信号并存** | 多个触发信号同时出现，互相印证 | 新调研 + 评审反复 + 用户诉求三者叠加 |

> **判定原则**：优先信号（P0 缺口 / 用户诉求）**直接触发**；次要信号（评审反复）
> 需累计 **≥3 次** 才触发，防止误升级。

---

## 二、评估流程（升级前必须完成的四步）

> 触发升级后，按以下四步**依次**评估，全部完成并留痕后才进入决策。

### 2.1 升级影响面

| 评估项 | 内容 |
|--------|------|
| 影响范围 | 哪些模块 / 角色 / 流水线 / 文档受影响 |
| 兼容性 | 升级后是否向后兼容？已有数据 / 任务 / 记忆是否受影响 |
| 回退路径 | 升级失败如何回退？回退到哪个版本 |
| 迁移成本 | 需要迁移什么？迁移工作量多大 |

### 2.2 可行性

| 评估项 | 内容 |
|--------|------|
| 技术可行性 | 现有架构 / 技术栈能否支撑升级 |
| 资源约束 | 所需人力 / 时间 / 计算资源是否满足 |
| 依赖完整性 | 升级是否依赖其他未完成的模块 / 能力 |
| 分步策略 | 能否分阶段升级？最小可行升级是什么 |

### 2.3 风险评估

| 风险项 | 等级 | 缓解措施 |
|--------|------|---------|
| 功能回退 | 高 / 中 / 低 | 测试信号灯 + 回退路径 |
| 兼容性破坏 | 高 / 中 / 低 | 版本兼容层 / 迁移脚本 |
| 团队适配 | 高 / 中 / 低 | 升级文档 + 培训 + 过渡期 |
| 数据迁移 | 高 / 中 / 低 | 数据备份 + 迁移验证 |

> **风险评估必须输出**：风险等级 + 缓解措施 + 是否可以接受（可接受 / 需缓解后接受 / 不可接受）。

### 2.4 优先级

| 优先级 | 判定标准 | 示例 |
|--------|---------|------|
| **P0** | 升级影响核心功能 / 安全 / 数据完整性，不做会出大问题 | 评审修复闭环的上下文路由机制 |
| **P1** | 升级显著提升效率 / 质量，但现有功能可用 | 共享记忆的版本管理增强 |
| **P2** | 升级锦上添花，不影响现有功能 | 文档格式统一 |

## 三、决策机制（由谁拍板）

> **核心原则：升级决策权归人类**。CodeBuddy 只做评估和建议，不自行执行框架升级。

### 3.1 决策流程

```
触发条件满足 → CodeBuddy 输出升级评估报告（影响面 / 可行性 / 风险 / 优先级）
    │
    ▼
CP（暂停确认点）暂停 → 在 PR / Issue 评论中 @ 人类拍板
    │
    ├── 人类批准 → 进入落地执行（3.2）
    ├── 人类打回 → 记录打回原因，停止或调整后重评
    └── 人类搁置 → 记录搁置原因，进入待升级队列
```

### 3.2 落地执行

| 阶段 | 动作 |
|------|------|
| 拆分任务 | 将升级拆为**可独立验证**的子任务 |
| 实施升级 | 按子任务逐一实施，每个子任务跑测试信号灯 |
| 验证通过 | 全部子任务测试通过后，标记升级完成 |
| 版本更新 | 更新框架版本号（见第四节版本演进线） |

> **升级落地必须走 PR**：CodeBuddy 只提交 PR，由人类确认合并。

## 四、版本演进线（如何平滑升级到下一版）

### 4.1 版本号约定

```
v{主版本}.{次版本}.{补丁版本}

主版本：框架架构级变更（不向后兼容）
次版本：功能级增强（向后兼容）
补丁版本：Bug 修复 / 小改进
```

### 4.3 升级流程

```

    → 更新本文档（版本演进线 + 升级记录）→ 标记完成
```

## 五、落地留痕（只增不改只追加）

> 每次升级必须在共享记忆 / 本文档中留痕，**只增不改只追加**，保证全程可回溯。

### 5.1 升级记录写入内容

| 字段 | 说明 |
|------|------|
| `upgrade_id` | 升级唯一标识（如 `UPG-001`） |
| `trigger` | 触发条件（新调研 P0 / 评审反复 / 用户诉求 / 10 轮超限 / 多源叠加） |
| `scope` | 影响面（模块 / 角色 / 流水线 / 文档） |
| `risk` | 风险等级（高 / 中 / 低）+ 缓解措施 |
| `priority` | P0 / P1 / P2 |
| `decision` | 人类拍板结果（批准 / 打回 / 搁置）+ 原因 |
| `implemented` | 落地子任务 + PR 链接 + 版本号 |
| `timestamp` | 留痕时间 |
| `status` | `active`（当前生效）/ `superseded`（被更新版本覆盖） |

### 5.2 写入规则

- **只增不改只追加**：每次升级记录追加到文档末尾 / 共享记忆，不修改历史记录；
- **旧记录保留**：被新版本覆盖的升级记录标记 `status=superseded`，物理保留；
- **可回溯**：任何升级均可从记录追溯触发条件 → 评估 → 决策 → 落地全过程。

### 5.3 共享记忆写入位置

```
loc://memory.framework_upgrade.content.<seq>  框架升级记录（结构化）
loc://memory.framework_upgrade.task.<seq>    升级任务卡
loc://memory.framework_upgrade.skill.<seq>   升级经验沉淀
```

## 七、一句话总结

**触发（新调研 P0 / 评审反复≥3次 / 用户诉求 / 10轮超限 / 多源叠加）→ 评估（影响面/可行性/风险/优先级）→ 人类 CP 拍板 → 落地走 PR → 留痕只增不改只追加**，让框架版本平滑演进、全程可追溯。

## 八、落地接线状态

> 本节记录框架自升级闭环的落地接线进度（wp_server 程序线·cto）。

### ✅ 已完成（v0.6.4）

1. **共享记忆接线**：`framework_upgrade` 空间已与 `SharedMemory` 对接，
   写入位置 `loc://memory.framework_upgrade.{content|task|skill}.<seq>`
   可直接通过 `FrameworkUpgradeMemory` 调用；
2. **UPG 编号递增规则**：`next_upg_id()` 自动扫描共享记忆已有记录，
   生成 `UPG-XXX` 递增编号，跨实例安全不重复；
3. **四环节闭环留痕**：`FrameworkUpgradeMemory.record_upgrade()` 一次调用
   完成「触发→评估→决策→落地」全部环节的共享记忆沉淀；
4. **只增不改只追加**：复用 SharedMemory 的不可变 + 版本链机制，
   升级记录写入后不可删改，修订通过追加新版本实现。

### 🔜 待推进（v0.7）

2. 测试线对触发/评估/决策/留痕四环节做验收测试（wp_testing）；
3. 人类 CP 对本次升级做最终拍板确认。
